## [2.5.1] — 2026-11-23

Published to npm as `@japofc/baileys@2.5.1` and tagged `v2.5.1`. Unlike 2.5.0, this release
really does contain the four new APIs listed below — the 2.5.0 tarball never did, which is
why those entries moved here.

### Added

> Moved here from the 2.5.0 entry, where they were listed by mistake. Verified against the
> published tarball: `@japofc/baileys@2.5.0` on npm contains none of these files. If you
> installed 2.5.0 expecting them, they are not there.

- **`estimateMessageSize()` — how big is this message, actually (§2.221).** Nothing in this library, or in any fork of it I could find, could answer that before a send. The content is built through the library's own `generateWAMessageContent()` and run through the real protobuf encoder, so the number is a measurement rather than a guess, and `heaviest` names the single largest field so you know what to cut. It never performs network I/O: remote media (`{ url }`, a stream) is reported as unmeasurable instead of being fetched, and an unknown media size is `undefined`, never `0`. `excludes` states plainly what the count leaves out (Signal encryption overhead, WebSocket framing, the media file body).

- **`createSendPacer()` / `SendPacer` — spread sends over time (§2.222).** Minimum spacing, bounded jitter, rolling per-minute and per-hour quotas, optional typing-time scaling, a bounded queue, and strict release ordering. Deliberately **not** called "anti-ban": nobody outside WhatsApp knows their enforcement rules, and a library that promises to prevent bans invites the exact risk-taking it claims to prevent. It is a queue with a clock, and the stats it returns say nothing about account safety. Every time source (`now`, `sleep`, `random`) is injectable, so pacing behaviour is tested to the millisecond with no real timers.

- **`preflightMessage()` — check a message before you send it (§2.220).** Every limit WhatsApp enforces was already encoded in this library, but only as a throw at send time, which means a bot learns its payload is invalid while a user is waiting. `preflightMessage(content, { jid })` runs the same checks offline and returns structured findings (`ok`, `errors`, `warnings`, each with a stable `code`) instead of throwing — including poll option counts, quiz-polls-outside-channels, caption length counted in code points, button/list/album/sticker-pack caps, malformed mention jids, and unresolvable media. It never throws, whatever it is handed; a validator that crashes is the failure it exists to prevent. A clean result means "nothing locally detectable is wrong", never "this will be delivered", and the result says so in `checked`. Also exported: `PREFLIGHT_LIMITS` and `formatPreflight()`.

- **`sock.newsletterAction(jid, action)` and `sock.newsletterReactionMode(jid, mode)` (§2.219).** Ported from community forks: a runtime-chosen channel action for bots driven by a config table, and control over who may react to channel posts. `newsletterAction` dispatches only over query ids this library already ships (FOLLOW/UNFOLLOW/MUTE/UNMUTE) — no invented protocol ids — and an unknown action or mode is rejected locally as a Boom 400 instead of failing opaquely at the server.

### Fixed

- **§2.225 `makeStatusMentionMessage({ attributionType })` now actually sends the attribution.** It was returned as a top-level `contextInfo`, a field `proto.Message` does not have, so protobufjs discarded it silently and every reshare went out unattributed. It is now placed on the quoted content's own `contextInfo`; the input object is not mutated and an existing `contextInfo` is preserved.
- **§2.226 passing a key with an explicit `remoteJid: undefined` no longer erases the `status@broadcast` default.** Object spread copies present-but-undefined keys, so `{ id, remoteJid }` lifted from a message without a `remoteJid` produced a key pointing nowhere. Fixed in all four status builders that compose a key; a real override still wins.
- **§2.227 `makeGroupStatusReactionMessage` no longer attaches a `contextInfo.parentGroupJid` that cannot be transmitted.** `ReactionMessage` has no `contextInfo` field; the group is identified by `key.remoteJid`. The field was removed rather than relocated, since the protocol offers no valid home for it.
- **§2.223 `useSingleFileAuthState().saveCreds()` now actually saves before it resolves.** It queued a debounced write and returned immediately, so a process that exited within three seconds of pairing lost its session and had to scan a new QR code — while `useMultiFileAuthState().saveCreds()` had always written synchronously. New `flush()` and `close()` methods force pending key writes, and the debounce timer no longer holds the event loop open.
- **§2.224 the single-file credential store is created 0600.** It was created with the default umask (0644 on most systems) while every later write used 0600, leaving the session world-readable on a shared host until the first flush.
- **§2.219 `newsletterUpdate()` could not send a settings-level change.** `settings` was hardcoded to `null`, correct for name/description/picture edits but silently dropping anything else. Callers may now pass `settings` explicitly; omitting it keeps the previous wire shape exactly.
- **A moderate `minimatch` advisory (GHSA-g3hv-75wg-m249) is documented, not silenced.** An earlier draft of this entry claimed it was fixed by an override to `minimatch@^11.0.9`. That claim was wrong and the override has been removed: minimatch 11 dropped `Minimatch.prototype.matchOne`, and typedoc 0.28.20 — the newest release — still requires `minimatch@^10.2.5` and crashes with `mini.matchOne is not a function`. The docs build on CI is what caught it. The advisory is first patched in 11.0.1, so today there is no version that is both patched and usable by typedoc. `typedoc` is the **only** dependant (devDependency), the impact is a glob-amplification DoS in our own documentation generator run over our own sources, and nothing reaches an installed package. `npm audit --audit-level=high` is clean; a plain `npm audit` reports 2 moderate entries and that is accurate. `npm audit fix` still proposes downgrading typedoc to 0.23.25, which remains the wrong trade.
- **§2.218 `RelayRtcTransport.closeAll()` could leave a WebRTC peer connection open.**
  A connect started just before the call built its peer after `closeAll()` had already
  swept the map, and an unclosed `RTCPeerConnection` keeps libuv handles alive — so a
  process that had hung up its last call never exited. `closeAll()` now latches the
  transport shut and in-flight connects refuse to build on it.
- **§2.216 `listDomains(prefix)` escaped LIKE patterns differently on each SQL backend.**
  A prefix ending in a backslash swallowed the wildcard on MySQL and Postgres, turning
  "every domain starting with X" into "the one domain named X" — verified against real
  Postgres and MySQL servers, where the old code returns the domain `back%` for the
  prefix `back\`. All three now share one escaping helper and state `ESCAPE` explicitly.
- **§2.215 a store adapter used before `init()` now says so.** `createSqliteStoreAdapter()`
  and `createMongoStoreAdapter()` threw `Cannot read properties of undefined (reading
  'get')`; they now throw an error naming the adapter and the missing call.
  `makePersistentStore()` was never affected — it calls `init()` for you.
- **§2.214 two SQLite tests pinned the absence of `better-sqlite3` as the spec** and went
  red the moment the optional peer was installed. They now assert the real contract and
  branch on driver presence.
- **§2.212 `generateProfilePicture()` reported a size it had not produced.** On the
  `@napi-rs/image` backend, `cover` returned a 300x300 image from a 600x300 source while
  the return value claimed `{ width: 720, height: 720 }` (napi never upscales), and
  `contain` handed back the original picture — not square, never letterboxed. All three
  backends now produce an exact `w x h` square and agree with each other.
- **§2.213 stickers were cropped instead of fitted without sharp.** The `@napi-rs/image`
  branch of `_toStickerWebP()` used the default `ResizeFit.Cover`, which crops to fill the
  512 square; a 600x300 sticker lost a third of its content. It now uses `Inside`, matching
  the sharp branch, with `jimp` covering the enlargement napi refuses to do.
- **CI (Node 24): `sharp` missing broke two suites, and the first fix was half right.**
  `sharp` was declared only as an optional peer, so `npm ci` never installed it and
  `tests/pairing-and-avatar.test.js` + `tests/v2410-batch-ci.test.js` died with
  `ERR_MODULE_NOT_FOUND`. It is a devDependency now **and** both suites probe for it and
  skip with a stated reason instead of hard-failing — because `sharp` has no Android
  binary, so a hard requirement breaks Termux. CI fails loudly if `sharp` or `ffmpeg` is
  absent, so a skip can only happen on a developer machine, never on CI.
- **A static `import sharp` took down tests that do not need it.**
  `v2410-batch-ci.test.js` imports `sharp` at the top, so on a platform without it the
  whole FILE failed to load, including the group-cache and anti-delete suites that touch
  no image code at all. The import is now a probe scoped to the sticker suite.
- **Termux/Android install documented and scripted** (`docs/faq.md`): `npm run
  install:termux` (`--ignore-scripts`) plus `pkg install ffmpeg`. `requireFfmpegPath()`
  already falls back to a system `ffmpeg` on `PATH`, and image work falls back to `jimp`,
  so nothing is lost — this just stops `npm ci` from failing halfway and leaving a broken
  `node_modules`.
- **A skip that lied: two ffmpeg tests never ran anywhere.** `v2410-voip-video-controls.test.js`
  probed for a bare `ffmpeg` on `PATH`, but the library resolves ffmpeg via
  `requireFfmpegPath()` (the `ffmpeg-static` devDependency). On CI and any dev machine
  without a system ffmpeg, the §2.174 I420 frame tests reported "ffmpeg not installed" and
  were skipped — green, untested. They now use the same resolver as the code and pass.
- **`v2410-batch-by.test.js` would have died on a platform without `whatsapp-rust-bridge`**
  (an optionalDependency), by static import. It now probes and skips with a stated reason;
  the bridge's absent-platform contract is covered in `v2410-lt-hash.test.js`.

### Changed

- **New test hook `_setImageProcessingLibrary()`.** `getImageProcessingLibrary()` caches
  the first backend it finds (sharp > @napi-rs/image > jimp), which made the other two
  branches unreachable for tests — that is how §2.212 and §2.213 survived a green suite.
  The hook pins a backend, or resets with `null`. Underscore-prefixed: a test seam, not
  part of the supported surface.
- **`better-sqlite3`, `fluent-ffmpeg`, `@napi-rs/image`, `@roamhq/wrtc`, `pg`, `mysql2`, `ioredis`, `mongodb` and the in-memory doubles `pg-mem` / `ioredis-mock` are devDependencies now.** Both are optional peers
  used by `lib/`, and none was installed in development, so their code paths were never
  executed by anything. That is pattern 38, and it has now produced four bugs (§2.209,
  §2.212, §2.213, §2.215) plus a broken test pair (§2.214). CI verifies all four are
  present so their suites cannot skip themselves green.
- **`sharp` is a real devDependency now** (was an optional peer only). CI's `npm ci` did
  not install it, so two suites that import it died with `ERR_MODULE_NOT_FOUND` on Node 24
  instead of running. It remains an *optional peer at runtime* — nothing changes for your
  install; this only guarantees the image tests actually execute. CI verifies its presence
  the same way it verifies ffmpeg.
- **Internal release notes are no longer packaged.** `PASTE-LIST-*.md` and `ANNOUNCE-*.txt`
  were working notes sitting under `docs/`, which `files` ships wholesale. They now live
  outside the repository. Tarball: 713 → 711 files. The published 2.5.0 predates them and
  is clean.

## [2.5.0] — 2026-10-01

> **Why 2.5.0 and not 2.4.10.** This round changes observable behaviour in public API, so a
> patch number would have been a lie: `redactSecrets()` no longer returns something
> `instanceof` your class, link previews make an extra request, `getHttpStream()` caps
> redirects at 5, LiveMessage's `onError` takes a third argument, and several internal id
> shapes changed. None of it should break a normal bot, but "should not" is a minor, not a
> patch. See **Changed** for the full list.

### Added



- **The four networked store adapters are tested against real databases.** `createPostgresStoreAdapter`, `createMysqlStoreAdapter`, `createRedisStoreAdapter` and `createMongoStoreAdapter` are public exports that had never been run against the servers they target. CI now starts Postgres, MySQL, Redis and MongoDB as service containers and fails if any is unreachable, so the suite cannot skip itself into a green run. Locally, set `JAP_TEST_POSTGRES_URL`, `JAP_TEST_MYSQL_URL`, `JAP_TEST_REDIS_URL` and `JAP_TEST_MONGO_URL` to opt in.

- **New: `Digest` (`docs/digest.md`).** Collect many small events and post one summary per
  window instead of a message each. Bounded buffer that keeps counting past the cap,
  de-duplication with counts, explicit overflow reporting, silence on an empty window,
  atomic flush (late events land in the next window, never lost or doubled), aligned
  release times, and `toJSON()`/`restoreDigest()` so a restart does not lose the open
  window. **New exports:** `createDigest`, `restoreDigest`, `renderDigest`, `startDigest`,
  `DIGEST_WINDOWS`, `DEFAULT_MAX_EVENTS`, `DEFAULT_MAX_LINES`.
- **New: `Quorum` (`docs/quorum.md`).** Group decisions that count their own votes and lock
  themselves: eligibility, one ballot per voter, early rejection once approval is
  arithmetically impossible, veto, expiry as a real outcome, and `onResolve` firing exactly
  once after the final frame. The core is pure — no socket, no timers — and `sendQuorum()`
  posts it as a self-updating message. **New exports:** `createQuorum`, `renderQuorum`,
  `sendQuorum`, `QUORUM_VOTES`, `QUORUM_TERMINAL`, `BUILD_TAG`.
- **Provenance: `BUILD_TAG` and `mintId()` are now shared.** Feature ids are minted through
  one helper instead of each module rolling its own, so the attribution tag spreads by
  default. `LiveMessage` now carries a tagged correlation id (`live.id`, also passed to
  `onError`); it is used for logs and is never written into the message body.
- **Provenance: attribution-trace detection.** `findAttributionTraces()` and the scanner now
  look for the leftovers a find-and-replace rebrand misses — alternate spellings, the npm
  scope, the ~800 `JAP@Fix` comment tags, exported symbol names, and ids derived from the
  attribution constants at runtime. **New exports:** `findAttributionTraces`,
  `ATTRIBUTION_TRACES`.
- **New: `LiveMessage` (`docs/live-message.md`).** One message that keeps itself up to date
  instead of a chat full of progress spam. Updates coalesce into throttled edits, identical
  renders are never sent, there is a hard edit budget, edits never overlap, and every exit
  path clears the timer. Background failures go to `onError` and are never thrown
  asynchronously. **New exports:** `createLiveMessage`, `progressRenderer`,
  `startProgressMessage`, `MIN_THROTTLE_MS`, `DEFAULT_THROTTLE_MS`, `DEFAULT_MAX_EDITS`,
  `MAX_CONSECUTIVE_ERRORS`.
- **New: provenance tooling (`docs/provenance.md`).** Rename-resistant fingerprints for this
  project's own modules, a scanner that recognises them inside a third-party package even
  after every identifier has been renamed and the code reformatted, and
  `verifyProvenance()` to check that the attribution the licence requires is still attached.
  **New exports:** `PROVENANCE`, `tokenizeForFingerprint`, `fingerprintSource`,
  `sketchSimilarity`, `matchAgainstManifest`, `verifyProvenance`, and the related constants.
  **New scripts:** `npm run provenance:manifest`, `npm run provenance:scan -- <path>`.
  Nothing runs on import: no network access, no automatic logging, no self-check, no
  behaviour change for anyone who does not call it.

- **New: `createPinnedFetch()` and `createPinnedLinkPreviewFetcher()`
  (`docs/ssrf-hardening.md`).** A `fetch`-compatible client that connects to the exact IP
  address the SSRF guard validated, instead of handing the hostname back to `fetch` to
  resolve a second time. Closes the DNS-rebinding window §2.211 documented and left open.
  Opt in with `getHttpStream(url, { pinDns: true })`, `resolveSafeRedirectUrl(url, {
  pinDns: true })` or `getUrlInfo(text, { fetchOpts: { pinDns: true } })` — the last one
  also stops calling `link-preview-js`, since a library doing its own fetching cannot be
  pinned by any option we pass it.

### Changed

- **Internal ids now carry the build tag.** `scheduling`, `templates`, `auto-reply`,
  `poll-extras` (side-by-side polls), `payment` (request and reminder ids) and `html-app`
  session ids are minted through `mintId()`. They also stop using `Math.random()` for
  identifiers. **Wire-protocol ids are untouched** — `generateMessageID()`,
  `generateStatusMessageId()` and the Bloks `decision_id` keep their WhatsApp-mandated
  shapes.
- **`redactSecrets()` returns a redacted plain object** for class instances, Maps, Sets and
  Errors instead of the original reference (§2.205, detailed under Fixed). If you relied on
  `instanceof` surviving redaction, that no longer holds — the return value is a copy meant
  for logging, never a working object.
- **`pinDns` is opt-in, not the default.** Pinning trades `link-preview-js`'s richer
  metadata parsing for a guarantee about where the socket goes, and bypasses any custom
  `dispatcher`. Defaults are unchanged; turn it on where untrusted URLs are fetched.
- **Link previews make one extra request** (§2.211): the redirect chain is resolved under
  the full SSRF guard before the preview library is called. `fetchOpts.resolveRedirects:
  false` restores the old single-check behaviour.
- **`audio-decode` is a devDependency now**, so the waveform path is exercised on every test
  run. It remains an optional peer at runtime — nothing changes for your install.

### Fixed

- **A `usernameQueryIds` entry with no value no longer disables every username call
  (BUGREPORT §2.140).** `makeWASocket({ usernameQueryIds: { CHECK: process.env.WA_CHECK_ID } })`
  with the variable unset used to overwrite the pinned fallback id with `undefined` and
  register the key as a deliberate manual pin, so auto-rotation refused to repair it and
  `checkUsername()` threw "query_id not configured" for the lifetime of the socket. Only a
  non-empty string counts as an override now.
- **Videos now carry their dimensions (§2.178).** `sendMessage(jid, { video })` without an
  explicit `width`/`height` shipped with none, because only the image path ever computed them —
  so clients laid the video out in a wrongly-shaped placeholder until it downloaded. A single
  unscaled frame is probed and its JPEG frame header read (no new dependency).
- **`extractVideoThumb()` defaults to a 32px width (§2.179)** like its image sibling, and
  rejects a bad `size.width` by name instead of handing `scale=undefined` to ffmpeg.
- **`voip.createCallLink({ video })` (§2.180).** Creating a link was only possible through the
  socket; the VoIP client could preview and join links but not make one.
- **Video thumbnails work again on ffmpeg 7 (§2.177).** `extractVideoThumb()` asked for the
  mjpeg encoder without a pixel format; ffmpeg 7 rejects limited-range YUV outright and exits
  234, so every video thumbnail failed. It now requests `yuvj420p`. CI installs ffmpeg so the
  tests that cover this actually run instead of skipping.
- **A stale unbind handle no longer stops session-health tracking (§2.185).**
  `createSessionHealthMonitor().bind()` returned the same `unbind` every time, so calling an
  off() kept from a previous binding tore down the current one — after a reconnect, tracking
  stopped silently.
- **Link previews now resolve redirects under the full SSRF guard (§2.211).** The first URL
  was DNS-checked and every redirect after it got only a hostname comparison, because
  `link-preview-js` hands redirects to a synchronous callback. The chain is resolved up
  front instead. **New export:** `resolveSafeRedirectUrl(url, options)`. Costs one extra
  request; `fetchOpts.resolveRedirects: false` opts out. `fetchOpts.allowHosts` is now
  honoured by the URL guard as well as the thumbnail fetch.
- **`startVideoPreview()` is reachable now (§2.210).** The VoIP engine has exposed it all
  along with nothing on `VoipClient` calling it, so the only route was the unsupported
  `engineCommand()` escape hatch. `callId` defaults to the active call and `selfJid` to your
  own JID; both throw clearly when they cannot be resolved.
- **Voice-note waveforms actually work now (§2.209).** `getAudioWaveform()` assumed every
  decoder returns an `AudioBuffer`; `audio-decode` 3.x returns a plain object for WAV, so
  the call threw into a debug-level `catch` and the function returned `undefined`. Both
  shapes are handled, and `audio-decode` is now a devDependency so this path is tested on
  every run instead of being skipped.
- **Short voice notes get a real waveform again (§2.208).** Clips under 64 samples divided by
  a block size of zero, producing `NaN`s that `Uint8Array` silently turned into a flat line.
  **New export:** `computeAudioWaveform(rawData, samples?)`, the pure arithmetic behind
  `getAudioWaveform()`, usable without the optional `audio-decode` dependency.
- **The SSRF guard now applies to redirects (§2.207).** `getHttpStream()`/`fetchBuffer()`
  checked the URL you passed and then let `fetch()` follow a `302` anywhere — including
  loopback and cloud metadata addresses. Every hop is validated now, with a redirect cap
  (`maxRedirects`, default 5). `uploadWithNodeHttp()` re-checks its redirects too.
- **`redactSecrets()`/`secureLogger()` no longer leak the secrets they exist to hide
  (§2.205).** Anything that was not a plain object — including the auth state when it comes
  from a class — was passed through untouched and printed in clear text.
  **Behaviour change:** `redactSecrets()` now returns a redacted *plain object* for class
  instances, Maps, Sets and Errors instead of the original reference, so
  `result.x instanceof YourClass` is no longer true. The return value is a copy for logging,
  never a working object; an instance with no own enumerable properties is still passed
  through unchanged.
- **The pairing rate limiter forgets expired keys (§2.206)** instead of keeping one map entry
  per phone number forever; `limiter.trackedKeys` exposes the count.
- **`checkHtmlApp({ allowExternal: false })` can no longer be walked past (§2.201).** Unquoted
  (`src=https://…`) and protocol-relative (`src="//…"`) references were invisible to the
  check, so a bundle that loads remote code was reported as clean.
- **The member-label timestamp is unix seconds, not milliseconds (§2.202)**, and the label
  length limit is now 30 everywhere instead of 25 in one builder and 30 in three other
  places (§2.203).
- **`forwardRichResponse()` accepts the sockets it actually uses (§2.204)** — it checked for
  `relayMessage` and then called `sendMessage` — and no longer leaks its options into the
  message content.
- **Several library helpers could terminate your process (§2.196–§2.199).** `groupLabel()`,
  the message scheduler's timer, button-sender's local echo and auto-update's `onError` all
  started async work whose rejection had nowhere to go — and an unhandled rejection kills a
  Node process by default. Each now contains its own failures.
- **A scheduled message that was delivered is no longer reported as failed (§2.200).** A
  throwing `onSent` callback fell into the send's error handling, so `onFailed` fired for a
  message that had already gone out — and retrying on that sent it twice.
- **CSV chat exports are no longer a formula-injection vector (§2.195).** A message beginning
  with `=`, `+`, `-` or `@` was written into the file as-is, so opening your own export in
  Excel or Sheets could execute a formula a stranger sent you.
- **`quizSection({ shuffle: true })` actually shuffles (§2.193).** It used the
  `sort(() => Math.random() - 0.5)` idiom, which is measurably biased.
- **Survey item ids no longer collide within one millisecond (§2.194).**
- **Animated stickers stay animated (§2.186).** Conversion read only the first frame, so an
  animated GIF became a still sticker and reported itself as not animated. The three copies of
  this conversion are now one helper; the pack cover stays a still deliberately.
- **A WebP sticker is actually fitted to 512 (§2.187)** instead of being passed through at
  whatever size it arrived.
- **`createGroupMetadataCache` no longer leaks the socket it was told to forget (§2.188).**
  A destructured `bind()` threw, rebinding left the old socket's listeners attached, and
  `unbind()` could not clean them up afterwards.
- **The group cache evicts LRU, as documented (§2.189)** — reads used not to count as uses.
- **A burst of sends to one uncached group makes one query, not one per send (§2.190).**
- **Anti-delete works for the revoke shape that actually arrives (§2.191).** A revoke key
  carrying only `id` looked up `undefined:id` and recovered nothing.
- **`MessageStore.clearChat()` also forgets that chat's recovered deleted messages (§2.192).**

### VoIP
- **The remote participant's video is no longer thrown away (§2.182).** Every inbound frame was
  decoded by the stack and dropped because nothing listened for it. Calls now emit a `video`
  event, and `call.recordVideoToFile(path)` writes an mp4 (it stops, loudly, if the resolution
  changes mid-call rather than writing a torn file).
- **Call recordings can contain both sides (§2.183).** `recordToFile()` only ever heard inbound
  audio; what you send was unobservable. There is now an `audio-out` event, and
  `recordToFile(path, { mix: true })` writes a stereo wav with the peer left and you right.
- **`voip.setParticipantSubscriptions(jids, qualities)` (§2.184)** — pick who you receive, and
  at what video quality, in a large group call.
- **Video calls can actually send video (§2.174).** `VideoFeeder` shipped in §2.85 and was never
  connected to anything: there was no frame uplink on the engine, no listener for the worker's
  video-capture callbacks, and no video source on a call, so `useVideo: true` set a flag and sent
  nothing. The chain is now complete, with `videoSource` on `call()`, `answerCall()`,
  `joinGroupCall()` and `startGroupCall()`, mid-call `setVideoSource()`, and
  `setVideoMuted` / `pauseVideo` / `resumeVideo` / `requestVideoUpgrade` / `acceptPeerVideo` /
  `requestKeyFrame` on the call.
- **Screen sharing and the waiting room are reachable (§2.175).** Fifteen commands the WASM
  worker already accepted had no wrapper: `startScreenShare`/`stopScreenShare`,
  `admitToCall`/`denyFromCall`/`admitAllToCall`/`setWaitingRoomEnabled`, `sendWave`,
  `notifyViewChange` and the video controls above. Plus `engineCommand(name, args)`, a
  documented escape hatch that is explicitly **not** covered by semver.
- **Call quality is readable (§2.176).** `getCallQuality()` parses the engine's stat string into
  `{ callId, raw, metrics }`, and `monitorCallQuality({ intervalMs })` emits `call-stats` while a
  call is up, stopping itself when the call ends.
- **An injected `config.engine` works before `connectWithSocket()` (§2.175).**
- **Split bills report the right settled total (§2.167).** `readSplitPaymentMessage()` summed
  raw wire values and divided by the *total's* offset, so a participant row stored with a
  different offset was off by the ratio between the two — 150.00 of 300.00 paid read back as
  15.00 settled. Each row is now read in its own units.
- **`readPaymentMessage()` accepts the object `buildSplitPaymentMessage()` returns (§2.168).**
  It previously only matched the wrapped `{ splitPaymentMessage }` form.
- **List and buttons messages are detected inside every view-once wrapper (§2.169).** Under
  `viewOnceMessageV2`/`viewOnceMessage` they got an empty `<biz/>` node and did not render.
- **`patchMessageForMdIfRequired()` no longer drops device-list metadata (§2.170)** when the
  message carries its own `messageContextInfo`.
- **A text-only header no longer hides a button payload's media (§2.171).**
- **Album headers no longer announce items that are never sent (§2.172).**
- **`botMetadataCertificate()` rejects a length it cannot encode (§2.173)** instead of silently
  returning a truncated, unparsable header.
- **`useSqliteAuthState()` now works the way the docs described it (§2.163).** The guides
  showed `{ database: './auth.db' }`, which threw `TypeError: db.pragma is not a function`
  because `database` expects an open handle. The docs now say `dbPath`, and a string passed as
  `database` is accepted as a path so existing copies of that snippet start working.
- **`useSqliteAuthState()` creates a nested `dbPath` directory (§2.164)** at `0700`, matching
  `useMultiFileAuthState`.
- **The SQLite auth database is no longer world-readable (§2.165).** It was created at the
  process umask; it and its `-wal`/`-shm` sidecars are now `0600`.
- **A corrupt SQLite creds row reports itself clearly (§2.166)** instead of a bare
  `SyntaxError`. It still refuses to start a fresh session — see §2.161.
- **`useJAPDBAuth()` refuses to start a fresh session over a corrupt auth file (§2.161).** It
  used to treat an unparseable file as an empty state, pair as a new device, and overwrite the
  damaged file on the first save. `useMultiFileAuthState` already refused; the two now agree.
- **One failed auth write no longer stops all later ones (§2.162).** `useJAPDBAuth`'s write
  queue inherited the rejection, so a single transient disk error silently ended persistence
  for the life of the process.
- **Failed atomic writes no longer leak temp files (§2.159).** `useMultiFileAuthState` left
  `*.tmp-<pid>-<ts>` behind on failure, and `pruneStaleAuthFiles` could not see them — which
  undercut the inode-exhaustion guard the adapter was hardened for. Prune now collects orphans
  too (`orphanTmp`, on by default).
- **The per-file auth mutex table no longer grows without bound (§2.160).**
- **`autoReconnect().stop()` now really stops (§2.155).** A `stop()` that landed while the
  socket factory was still running left the resulting socket open and unmanaged — likely on
  Ctrl-C, since `makeWASocketAuto` fetches the WA version over the network.
- **`chunkText()` no longer hangs on a bad size (§2.156).** A size of `0` or `NaN` put it in
  an infinite loop; it now throws a `RangeError`.
- **`progressBar()` no longer renders `" NaN%"` (§2.157).** A non-numeric value sailed through
  the clamp, because `Math.max(0, NaN)` is `NaN`.
- **`truncate()` keeps emoji whole (§2.158).** It cut on UTF-16 code units, so a family emoji
  could come back as a different single emoji.
- **BEHAVIOUR CHANGE — `normalizePhoneForPairing()` now rejects local numbers (§2.154).** It
  used to strip a leading `0`, turning `08123456789` into `8123456789` — a different number
  that passes validation and is then silently ignored by the server, so the pairing code never
  arrives. It now throws, naming the correct form. The `00` international prefix is still
  stripped. No internal caller is affected.
- **A longer command prefix is reachable again (§2.151).** `createRouter({ prefix: ['!','!!'] })`
  matched the first-listed prefix, so `!!cmd` never fired.
- **One person can no longer hold several poll votes (§2.152).** `createPollManager()` keyed
  voters on the raw jid, so the same human voting from two devices counted twice.
- **A duplicated poll option no longer double-counts a vote (§2.153).**
- **The sticker-pack media cache can no longer serve a different pack (§2.147).** The key was
  built from only the URL-based stickers and ignored the cover, name, publisher, description
  and packId. Packs mixing URLs and Buffers are no longer cached at all. New export:
  `stickerPackCacheKey()`.
- **`isAnimatedWebP()` no longer flags a still sticker as animated (§2.148).** It matched the
  bytes `ANIM` anywhere in the file, including compressed pixel data; it now walks the RIFF
  chunk list.
- **Signal keys are persisted before they are cached (§2.149).** If the store rejected a
  write, the cache kept serving keys that were never saved.
- **The in-memory store no longer strips `status` from your `messages.update` payload
  (§2.150).** It mutated the shared event object in place, so whether your handler saw the
  field depended on listener registration order.
- **Group stories are actually sent as group stories (BUGREPORT §2.143).** The
  `isGroupStatus` flag was being attached to the `messageContextInfo` envelope instead of the
  media node, so the server ignored it.
- **A malformed app-state index now fails with a clear error (§2.144).** It still throws —
  that is deliberate, see BUGREPORT §2.144 — but as a Boom carrying `reason: 'bad-index'`
  instead of a bare `SyntaxError`.
- **Deadline races no longer leak their timer (§2.145).** VoIP TC-token fetch, VoIP stack init
  and health-monitor probes each left a pending timer behind, keeping the event loop alive for
  the full timeout after the work had already finished. New exported helper:
  `raceWithTimeout(promise, ms, fallback)`.
- **`Shared.fetchBuffer()` honours its timeout when you pass your own signal (§2.146).**
  Previously a caller-supplied `signal` silently replaced the timeout controller.
- **An explicitly-undefined option no longer overrides its default (§2.142).** Affected
  `contextInfo` and `externalAdReply` in the interactive-message builder.
- **A malformed URL in an inbound message no longer throws (BUGREPORT §2.141).**
  `readMusicMessage()` and `readSocialPreview()` ran `new URL()` on `songUri`/`sourceUrl`
  straight off the wire, so a peer could crash the handler with an unparseable value. The
  derived host is now `null` for anything that will not parse (including `javascript:`-style
  URIs, which parse but have no authority); the raw field is returned untouched.
- **`normalizeStickers()` clamps a non-numeric position instead of emitting `NaN`.**
  `Math.max(0, NaN)` is `NaN`, so a bad `x`/`y` went out as `null`. It now falls back to the
  centre, and a non-numeric `scale`/`rotation` is dropped.
- **`sock.USERNAME_QUERY_IDS` is a snapshot, not the live internal map.** Writing to it used
  to change the id in effect while bypassing the manual-pin bookkeeping, so the next rotation
  silently reverted the write. Use `setUsernameQueryIds()`.
- **CI: `sharp` is optional, so the test suite must not hard-import it.**
  `tests/v249-profile-picture-crop.test.js` imported `sharp` at the top level even
  though it is an optional peer dependency. On a runner without a usable prebuilt
  binary the import threw and the entire file failed to load, so the Node 24 job went
  red while Node 20 and 22 passed. The cases that need `sharp` now resolve it the way
  the library itself does and skip when it is absent.
- **Release verification no longer resolves the wrong version.** The workflow read the
  version from `workflow_run.head_branch`, which reports `main` rather than the tag
  name when the tagged commit is also the head of the branch. Every release therefore
  tried to verify a package version called `main` and failed. The tag is now only
  trusted when it looks like a version, otherwise the registry is consulted.

### Fixed
- **`Bot.stop()` did not stop the bot** 🩹🛑 — it cancelled the reconnect timer and closed the stores but left the socket open with its listeners attached, so a "stopped" bot kept handling messages against a closed store, held the process alive, and **resurrected itself** when that socket eventually closed. `start()` likewise abandoned the old socket instead of closing it, so a double `start()` or a racing reconnect left two live sockets answering every message twice. **`stop()` is now async.** See BUGREPORT 2.136.
- **Overlapping durable-queue snapshots shared one temp file** 🩹💾 — concurrent `_persistQueue()` writers all used `${queueFile}.tmp-${pid}`, so a half-written snapshot could be renamed over a complete one. See BUGREPORT 2.138.
- **A timestamp the server never sent read as 1 Jan 1970** 🩹🕒 — the status and disappearing-mode usync parsers built `new Date(+(t || 0) * 1000)`, so a missing `t` became a real-looking 1970 date and a non-numeric one became an Invalid Date whose `.toISOString()` throws in your code. Missing is `undefined` now, `duration` is no longer `NaN`, and an unusable call timestamp falls back to the arrival time. See BUGREPORT 2.133.
- **usync protocol parsers were called unbound** 🩹🔗 — the dispatch table stored `protocol.parser` detached from its instance, so any parser reading `this` threw and the per-user catch swallowed it: that protocol silently vanished from every result. See BUGREPORT 2.135.
- **A `conflict` stream error could leave the socket hanging instead of reconnecting** 🩹🔌 — `new Boom()` throws unless the status is an integer of 400+, and `<stream:error code="conflict">` / `<failure reason="0">` / `<error code="not-authorized">` were passed through raw: the throw happened *inside* the handler that had to call `end()`, so the connection was never closed, `connection.update` never reported it, and nothing reconnected. All three sites now go through the exported `toBoomStatusCode()`, and a `conflict` still maps to `connectionReplaced`. See BUGREPORT 2.132.
- **The session-health monitor answered about a different contact than it tracked** 🩹🩺 — with a `keyBy` resolver (the LID↔PN unifier the module itself documents) failures were stored under the resolved key while `isHealthy()` / `getStatus()` / `reset()` looked up the raw jid, so a contact whose session had just died reported healthy and `reset()` cleared nothing; the public `record()` also bypassed the resolver and filed the contact twice. See BUGREPORT 2.129.
- **`maxTracked` did not cap anything during a failure burst** 🩹📈 — only *healthy* contacts were evicted, so 3000 failing contacts kept 3000 entries under `maxTracked: 10`; `bind()` also threw when destructured, the very style its doc comment shows. See BUGREPORT 2.130.
- **The retry manager overwrote its own default with `undefined`** 🩹🔁 — constructing `MessageRetryManager` without a count disabled `hasExceededMaxRetries()` entirely (`count >= undefined` is always false) and a message could be retried without limit; `parseRetryErrorCode('4abc')` half-parsed to `4`, a MAC error that forces a session recreation; and a throwing phone-request callback inside a bare `setTimeout` was an uncaught exception. `DEFAULT_MAX_MSG_RETRY_COUNT` is exported. See BUGREPORT 2.131.
- **`adminOnly` commands ran unguarded in private chats** 🩹🛡️ — the group-admin gate was written `adminOnly && isGroup && !isAdmin`, so in a DM it was skipped altogether and the command executed for anyone who sent it, while the help screen still said *Requires: group admin*. `botAdmin` had the same hole. Both now imply a group and deny with `group-only` outside one. See BUGREPORT 2.126.
- **`CommandRouter.handle()` could throw despite promising not to** 🩹🚦 — only the command handler was wrapped; a throwing `onUnknown` / `onPermissionDenied` / `onCooldown` / `onError`, or a throwing `isAdmin` / `isBotAdmin` / custom `permission`, escaped into the middleware chain. Notifications are logged and swallowed, a permission resolver that fails refuses the command instead of running it, and there is a final catch-all. See BUGREPORT 2.127.
- **The group-admin resolver cache never released a group** 🩹🧹 — the TTL was only checked on a hit, so every group the bot had ever seen stayed cached for the life of the process. Entries are pruned and capped at `maxEntries` (500), and the resolver exposes `cacheSize` / `clearCache()`. See BUGREPORT 2.128.
- **A 32-bit binary length decoded as negative and rewound the stream** 🩹🧬 — `readInt()` accumulated with `|=`, which is signed, so a `BINARY_32` length with the high bit set came back negative: `readBytes()` returned an empty slice and moved the decoder's cursor *backwards*, quietly turning the rest of the frame into garbage instead of raising an error. Lengths are unsigned now and a negative one is refused outright. See BUGREPORT 2.123.
- **A deeply nested frame overflowed the call stack** 🩹🧱 — nested lists recursed without a ceiling, so malformed input produced `RangeError: Maximum call stack size exceeded` instead of a protocol error. Depth is capped at the exported `MAX_BINARY_NODE_DEPTH` (512); real nodes nest under ten. See BUGREPORT 2.124.
- **An attribute named `__proto__` vanished while decoding** 🩹🏷️ — `attrs[key] = value` is swallowed by the prototype setter for that one key, dropping the attribute from the node (and standing open as a prototype-pollution sink). It is written with `Object.defineProperty` now. See BUGREPORT 2.125.
- **A `w:mex` error code could destroy the error it was reporting** 🩹📡 — `new Boom()` throws unless the status is a number of 400 or more, and WhatsApp's GraphQL layer answers with `0`, `200` or a symbolic string: those failures surfaced as `First argument must be a number (400+)` with the server's real message, code and payload gone. The status is clamped now (the original stays on `err.errorCode`), and a non-JSON body becomes a Boom naming the query instead of a bare `SyntaxError`. See BUGREPORT 2.120.
- **A page without a picture lost its whole link preview** 🩹🔗 — `info.images` was destructured even when absent, and with `uploadImage` set the missing image was passed to the uploader as `url: undefined`; either throw escaped and the title and description went with it. Image-less pages now return a text preview, and a non-`Error` throw is no longer turned into a `TypeError`. See BUGREPORT 2.121.
- **`ws.close()` hung forever after the server dropped the socket** 🩹🔌 — `close()` awaited a `close` event that an already-closed socket never emits again, so every shutdown or reconnect routine awaiting it stalled (515, conflict and stream-end are the normal ways a WhatsApp session ends). It now resolves at once for a closed socket, attaches its listener before closing, terminates after `WebSocketClient.CLOSE_GRACE_MS`, and `connect()` replaces a dead socket instead of refusing to reconnect. See BUGREPORT 2.118.
- **Numeric colours were silently dropped** 🩹🎨 — `assertColor()`'s `return` sat inside the `else`, so a colour given as a number (including the ones generated for styled text statuses) became `undefined` and the message went out in WhatsApp's default colours. Junk strings now return `undefined` instead of a value parsed out of nonsense. See BUGREPORT 2.119.
- **Catalogue products were always reported "in stock", and prices could be `NaN`** 🩹🛒 — `availability` was hard-coded while the server sends it in the node, and every number came from `+getBinaryNodeChildString(…)`, which is `NaN` when the node is absent ("price on request" listings, orders without a quantity or total). Availability is read, and missing numbers are `undefined`. See BUGREPORT 2.115.
- **A failed catalogue-image upload leaked its temp file** 🩹🗂️ — the `unlink` only ran on the happy path, so every failed or timed-out upload left a full-size copy of the image in `os.tmpdir()` for good; the copy loop also ignored back-pressure. Cleanup is in a `finally` and writes wait for `drain`. See BUGREPORT 2.116.
- **`newsletterCreate()` threw on its own success response** 🩹📢 — a channel created without a description comes back without a `description` object (and without `viewer_metadata`), and the parser read `.text` off both: the channel was created, the call threw, and the new channel's id was lost. Every field is optional now, and missing numbers stay `undefined` instead of `NaN`. See BUGREPORT 2.114.
- **Username validation enforced invented rules** 🩹🏷️ — it rejected names WhatsApp actually hands out (31–35 characters, `9to5.dev`, `name_`) and accepted ones the server refuses (`ja-p`, `www.shop`, `myshop.com`), and looked for a 6-digit username key where WhatsApp's is 4. The real rules are in place, every result now carries a stable `errorType` (`UsernameValidationError`), and `USERNAME_PIN_LENGTH` / `USERNAME_DOMAIN_SUFFIXES` are exported. See BUGREPORT 2.111.
- **The group sender-key memory was append-only** 🩹🧹 — device jids that left the group, got unlinked, or belonged to the addressing mode a group used *before* flipping pn→lid stayed in the map forever: unbounded growth, re-serialised on every group send, and a lingering record of ex-members' devices. Each send now keeps only the devices it enumerated. See BUGREPORT 2.112.
- **Out-of-order group messages were lost forever** 🩹📥 — sender-key records are stored as plain JSON, so a seed comes back as `{ type: 'Buffer', data: […] }`; the per-message key never coerced it, so replaying a *skipped* iteration — i.e. any late or out-of-order group message — threw `Expected Buffer instead of: Object` after the key had already been consumed. Permanent "Waiting for this message". See BUGREPORT 2.110.
- **The group sender chain ratcheted twice per message** 🩹🔁 — encrypting asked for `iteration + 1`, so every send skipped a step and filed the skipped step away as a dead message key: the sender-key record grew by one unusable key per message (up to ~317 KB) and was rewritten to the auth store on every single send, with every recipient mirroring the same dead key. See BUGREPORT 2.109.
- **Removed group members could still read the next messages** 🩹🔑 — on a membership change we cleared only `sender-key-memory`, the "who already received the key" bookkeeping. That is not a rotation: the following send re-distributed the **same** sender key, which the member we just removed already held, so they kept decrypting the group indefinitely (our own comment claimed the opposite). The key record itself is now dropped too, so the next send mints and distributes a fresh key. See BUGREPORT 2.108.
- **Short videos got an empty thumbnail** 🩹🎞️ — seeking past the end of a clip makes ffmpeg exit `0` with no frame written, and we trusted the exit code: every video shorter than the seek point (default 1s) produced a 0-byte `jpegThumbnail`, and `videoToJpeg()` returned an empty Buffer. It falls back to the first frame and refuses to return a non-JPEG. See BUGREPORT 2.105.
- **`AudioFeeder.stop()` could leave ffmpeg running forever** 🩹📞 — back-pressure pauses the decoder's stdout, so a bare `SIGTERM` never reached an ffmpeg blocked writing into that pipe: the child, its pipes and therefore the whole Node process stayed alive (this hung `node --test` on any machine with a real ffmpeg). Teardown now drains and destroys the pipes, escalates to `SIGKILL` after 400ms, and `unref()`s the child. See BUGREPORT 2.107.
- **LID chats were sent to PN devices, and re-queried USync on every message** 🩹🪪 — USync answers a LID query with the contact's PN id plus a separate `lid` field, so the LID-priority branch never matched and the device cache was keyed by the PN user while lookups used the LID user: a chat addressed by LID got `@s.whatsapp.net` devices **and** fired an extra IQ per send. Addressing now follows a pn→lid map, resolved entries are cached under both keys, and the cache-hit path keeps the resolved jid. See BUGREPORT 2.100.
- **`migrateSession()` gave up when the device-list cache was cold** 🩹🔑 — the `device-list` key only exists after a USync *fetch*, so a session restored from disk never migrated PN→LID and the next LID send had to re-fetch keys. The device it was handed is always a candidate now, and the stored array is no longer mutated in place. See BUGREPORT 2.101.
- **The VoIP worker bootstrap leaked a `parentPort` listener per subscriber** 🩹🧵 — one subscription per `addEventListener()` and per `WorkerSyncedMessagePort`, never detached, with no `removeEventListener` at all: a long call reached Node's `MaxListenersExceededWarning` and fanned every message through stale handlers. They share one dispatcher now, `removeEventListener` works, and ports can `close()`. See BUGREPORT 2.102.
- **Clearing a chat on the phone left every message in the store** 🩹🗑️ — `processSyncAction()` had no branch for `clearChatAction` (we *build* that patch ourselves), so it fell through to `unprocessable update`. It emits `messages.delete` `{ jid, all: true }` now. See BUGREPORT 2.103.
- **Duplicate business node, and carousel cards that lost their buttons** 🩹🔘 — the duplicate guard only looked for a literal `<biz>` tag, so a caller-supplied `<interactive>`/`<hsm>`/`<buttons>`/`<list>`/bot node got a second one appended; and `shouldIncludeBizBinaryNode()` missed carousels whose *cards* carry nativeFlow buttons, so those cards arrived dead. See BUGREPORT 2.104.
- **AI-rich cards carried an unparsable "verified bot" certificate** 🩹🔏 — `botMetadataCertificate()` wrote a DER `SEQUENCE` header and then randomised the length bytes too, so every chain we attached declared the wrong size and failed the first structural check — including by our own `verifyBotSignature()`. ### Fixed
- **An unreadable tc-token timestamp stopped privacy-token issuance** 🩹🎟️ — `shouldSendNewTcToken()` did bare arithmetic, so a protobuf Long (what an auth store actually returns), a `bigint` (which threw) or any junk became `NaN` and the answer was "never refresh", while its sibling `isTcTokenExpired()` called the same value expired. Both share one normaliser now, and anything unreadable means *refresh*. See BUGREPORT 2.97.
- **`sync-action-utils` / `tc-token-utils` were unreachable** 🩹📦 — the modules existed but nothing re-exported them, so `processContactAction`, `emitSyncActionResults`, `readTcTokenIndex`, `shouldSendNewTcToken` and `isTcTokenExpired` could not be imported from the package.
- **Deeply wrapped messages stayed wrapped** 🩹📦 — `normalizeMessageContent()` gave up after 5 `FutureProofMessage` layers, and WhatsApp stacks more than that (ephemeral + view-once + document-with-caption + edited + group-mentioned + a bot forward), so the app received a *wrapper* as the message and `getContentType()` answered with the wrapper name. It now unwraps until stable, with a cycle guard. See BUGREPORT 2.96.
- **Accepting an invite credited the chat instead of the inviter** 🩹✉️ — `groupAcceptInviteV4()` / `communityAcceptInviteV4()` sent `admin: key.remoteJid`, so an invite forwarded into a group told the server the *group jid* had invited us and filed the join stub against it. The stub also stored `JSON.stringify(creds.me)` (leaking our LID and push name) where a JID belongs. See BUGREPORT 2.94.
- **A stale group-metadata cache addressed PN groups as LID** 🩹👥 — `addressing_mode: groupData?.addressingMode || 'lid'` invented LID addressing for any cached metadata written before that field existed. The mode is inferred from the participant jids before defaulting, and an unusable cache is re-fetched with the reason logged. See BUGREPORT 2.95.
- **A failed group send poisoned the sender-key memory** 🩹🔑 — the "these devices have the key" map was persisted ~250 lines *before* `sendNode()`, so a send that died on the wire left the session believing it had distributed a sender key nobody received: the retry distributed nothing and the whole group saw "waiting for this message" until the key rotated. The memory is committed only after the stanza is actually sent now. See BUGREPORT 2.93.
- **The group-invite icon cache was never wired up** 🩹🖼️ — it existed, but `sendMessage()` never passed it, so every `{ groupInvite }` re-queried the icon (five invites = five queries, and an iconless group paid a failing 404 each time). One cache per socket now, configurable via `groupInviteThumbnailCache` and exposed on the socket. The builder also silently dropped `groupInvite.caption` / `groupInvite.groupName` (only `text`/`subject` were read) — both spellings work now. See BUGREPORT 2.92.
- **Read receipts shipped `null` ids and duplicates** 🩹✅ — a key without an id went out as `<item id=null/>`, and WhatsApp drops a receipt containing a malformed item, so the valid ids in the same stanza were never acknowledged either. Id-less keys are skipped now, ids de-duplicated per chat+participant, and a bulk read is split into stanzas instead of one oversized one. See BUGREPORT 2.91.
- **`msmsg` envelopes vanished without a trace** 🩹🕳️ — they were skipped with a debug line that logged `node.attrs.key` (not an attribute a message stanza has, so always `{}`) and no `messages.decrypt-failed` event, unlike every other undecryptable message. They are still skipped, but now with the real message key and an observable event. See BUGREPORT 2.90.
- **Plaintext channel posts were dated 1 Jan 1970 and never `fromMe`** 🩹📰 — the handler read the timestamp off the `message` child instead of the notification node (`+undefined` → NaN → 0), and hardcoded `fromMe: false` even when the notification named us as the author, so a bot's own channel posts came back looking incoming. Both fixed, with the author kept on the key and `newsletterServerId` preserved. See BUGREPORT 2.89.
- **pino was a hard dependency** 🩹📦 — an app pinned to `pino@8` installed a second pino just for us. pino is an optional peer now (`^8 || ^9 || ^10`): present → used exactly as before, absent → a built-in JSON-lines logger with the same shape takes over (`usingPino` tells you which). See BUGREPORT 2.88.
- **A non-pino logger crashed the Noise handshake** 🩹🪵 — `console`, a bunyan/winston-style logger, a pino v8 instance or a plain `{}` died with `TypeError: logger.child is not a function` from inside the handshake. `ensureLogger()` now adapts any logger (and `false` means silence); a real pino instance is passed through untouched. See BUGREPORT 2.87.
- **Optional dependencies were re-probed on every call** 🩹📦 — `sharp`/`ffmpeg` were imported ad hoc at each call site, so a bot without them paid a failed resolution per sticker/thumbnail instead of once, with a different error each time. `loadOptionalModule()` memoises success *and* failure and reports `Run: npm i <name>` when a feature really needs it. See BUGREPORT 2.86.
- **Interactive buttons were validated against a hardcoded list** 🩹🔘 — a `nativeFlowMessage` name WhatsApp had just started accepting still failed local validation (`name '…' not allowed`) with no way to override it. The names now live in one module and the validator reads a refreshable registry (`update()` / `enableAutoUpdate()` / `reloadExports()`). See BUGREPORT 2.85.
- **The startup banner could not be turned off** 🩹🤫 — it printed on every `makeWASocket()` with no opt-out, so clean CI logs and JSON streams needed a `console.log` monkey-patch. Now: `makeWASocket({ printBanner: false })`, `setBannerEnabled(false)`, or `JAP_NO_BANNER` / `NO_BANNER`; `isBannerEnabled()` reports the state. Default unchanged. See BUGREPORT 2.84.
- **An album with one unsupported entry failed mid-send** 🩹🖼️ — entries that were neither `{ image }` nor `{ video }` were invisible to the album header and only tripped the per-item check inside the send loop, after the header and the earlier items had already been relayed. The album is validated as a whole up front now, naming the offending index. The loop also stopped sleeping `delayMs` after the **last** item (a 3-item album wasted a full extra delay). See BUGREPORT 2.83.
- **Call audio frames aliased the WASM heap** 🩹🎙️ — the VoIP playback loop emitted a `Float32Array` *view* into live WASM memory as the call's `audio` chunk, so any listener that kept the frame (buffering, uploading, transcribing) read the next frame's audio instead — and a heap growth left it with zero samples. Frames are independent copies now (`copyPlaybackFrame()`). See BUGREPORT 2.82.
- **A corrupt plaintext `creds.json` silently destroyed the session** 🩹🔐 — the wrong-password guard in `useEncryptedFileAuthState()` only covered encrypted files; a truncated, empty or non-JSON plaintext `creds.json` still read as "fresh install", so a new identity was minted and the next `saveCreds()` overwrote the real one. Critical files now refuse to load instead, while non-critical key files still degrade to `null`. `useEncryptedSingleFileAuthState()` got the same guard plus a clear error for a payload with no `creds`. See BUGREPORT 2.81.
- **VoIP reconnects leaked the signaling bridge into the auth state** 🩹📞 — `SignalingBridge.init()` wrapped `authState.keys.set` and never unwrapped it, so each reconnect stacked another wrapper around a function that runs on nearly every message and kept the discarded bridge alive forever. The auth state is now patched once, bridges register as observers, and the original function is restored when the last one leaves. See BUGREPORT 2.80.
- **A relay connect failure could kill the whole process** 🩹📞 — the VoIP relay transport started every connection with an uncaught `void this.#ensureConnection(...)`, so on an install without the optional `@roamhq/wrtc` package (whose loader throws on purpose) simply receiving a relay list became an `unhandledRejection` — fatal on Node 15+. Failures now mark the connection failed and surface through the new `onTransportError` callback and the logger. See BUGREPORT 2.79.
- **`relay.getStats().droppedPackets` was always 0** 🩹📊 — drops only ever bumped a per-connection counter that nothing exposed, so the aggregate every caller reads never moved even while the transport was discarding traffic.
- **Clear/delete/archive stamped the wrong end of the chat** 🩹🗂️ — `chatModificationToAppPatch()` took the newest message positionally (`lastMessages[length - 1]`), so a store that hands chats back newest-first produced a `messageRange` ending at the **oldest** message. It now takes the actual maximum timestamp and emits the list oldest-first. See BUGREPORT 2.78.
- **Batched app-state patches all got the same version** 🩹🔁 — `extractSyncdPatches()` gave every version-less patch `collection.version + 1`, so applying N patches advanced our bookkeeping by one and the next resync re-fetched what we had already applied; a collection node without a usable `version` attribute wrote `NaN` into the patch (and from there into the stored state). Versions are now consecutive, a patch carrying its own version re-bases the rest, and an unusable collection version leaves the patch alone with a warning.
- **Resuming a media download returned an empty file** 🩹📥 — `downloadEncryptedContent(url, keys, { startByte })` (no `endByte`) computed its upper bound as `NaN` and sliced every decrypted chunk down to nothing, so a resumed transfer "succeeded" with 0 bytes. Both range bounds are now applied independently. An empty response body also stopped throwing `Cannot read properties of undefined (reading 'final')` and now reports `Media download returned an empty body` with HTTP 502. See BUGREPORT 2.77.
- **The AIRich one-liner silently dropped unknown keys and then sent an empty card** 🩹✨ — `jap(sock, { latex: 'E = mc^2' })` (and `task`, `widget`, `thinking`, `product`, `post`, `reels`, `bloks`, `quotaUpsell`, `socialEntity`, `contentItems`, `generating`, `inlineVideo`, `progressStatus`) produced a card with zero primitives that was still delivered, because the one-liner had no key for any of them; a typo like `tabel` behaved the same way. All fourteen now have keys, unknown keys throw with a "did you mean …?" suggestion, and sending a card with no content is refused. See BUGREPORT 2.76.
- **An app-state patch that could not be applied still advanced the saved version** 🩹🗂️ — `decodePatches()` committed the patch version (and the decoded hash) *before* the patch was known to be good, so a skipped or LTHash-failing patch left the collection claiming it had synced past mutations it never delivered. Because nothing threw, the existing force-snapshot recovery never fired and the mutations — mutes, pins, archives, stars, contact names, read markers — were lost for good, while the saved hash no longer matched the server's. Nothing is committed now until a patch decodes *and* verifies; the caller gets `incomplete`/`synced` and the socket retries with a snapshot. See BUGREPORT 2.75.
- **The whole interactive-message handler set was never wired into `sendMessage()`** 🩹🔘 — `sendMessage(jid, { text, interactiveButtons })` silently delivered a plain text bubble with the buttons stripped off, carousels did the same, and `{ requestPaymentMessage }`, `{ productMessage }`, `{ groupInviteMessage }`, `{ eventMessage }`, `{ pollResultMessage }`, `{ groupStatusMessage }` and `{ interactiveMessage }` all threw `Invalid media type`. The handlers existed and were exported — the socket just never constructed them. All nine shapes now route correctly. See BUGREPORT 2.73.
- **Group stories returned no message key** 🩹🔑 — `handleGroupStory()` handed back `relayMessage()`'s raw result, so it was the one send path where `result.key.id` was undefined.
- **`nativeFlow` emitted dead buttons instead of rejecting bad input** 🩹🧪 — a `buttonParamsJson` passed as an object reached the wire as `""` (protobuf cannot encode an object into a string field), so the button rendered normally and did nothing when tapped; a typo'd shorthand reached the wire as an empty `{}` with no error; and the object form `{ nativeFlow: { buttons, optionText } }` ignored its own offer/bottom-sheet fields. See BUGREPORT 2.74.
- **`autoReconnect()` reconnected forever on fatal closes** 🩹🔌 — only `loggedOut` ever stopped the chain, so `connectionReplaced` (another process owns the session), `forbidden` (banned number) and `multideviceMismatch` each spun up ~70 sockets in 150 ms, fighting the other session and hammering a restricted account. The manager now consults `classifyDisconnect()`, stops on fatal verdicts and reports them through the new `onFatal` callback — while `badSession` retries first and only gives up after 3 consecutive hits. See BUGREPORT 2.71.
- **96 relative specifiers in the shipped `.d.ts` files had no `.js` extension** 🩹🧩 — `lib/Utils/index.d.ts` re-exported 95 of its 113 modules extensionlessly, which does not resolve under `moduleResolution: node16/nodenext`, so the disconnect classifier, call-guard, i18n, quota, health-monitor and ~90 other modules were invisible to TypeScript consumers despite being exported at runtime. Our own tscheck gate missed it because `skipLibCheck: true` hides resolution errors inside `.d.ts`. See BUGREPORT 2.72.
- **SSRF guard: every IPv6 URL was refused, and mapped IPv6 slipped past the filter** 🩹🛡️ — `URL.hostname` keeps the brackets around an IPv6 literal, so `isIP()` said "not an IP" and every such URL went down the DNS path and failed with a misleading `Failed to resolve host`. Separately, IPv4-mapped IPv6 was matched by three literal string prefixes, so `::ffff:169.254.169.254` (cloud metadata), hex forms like `::ffff:7f00:1` and expanded forms were classified as public — latent only because the first defect happened to block them. Mapped/compatible IPv6 is now decoded and run through the IPv4 rules, and `fe80::/10` and `fc00::/7` are matched as ranges. See BUGREPORT 2.70.
- **Pairing guard: rejected requests still spent the rate-limit budget** 🩹🔑 — `withPairingGuard()` consumed both the per-phone and the global limiter before deciding, so a request it then refused had already burned a global slot. One number retrying in a loop drained the hourly global allowance and locked every other number out, with only a couple of requests actually sent; a globally-blocked phone also lost one of its own attempts. Slots are now spent only when the request really goes out. See BUGREPORT 2.69.
- **Persistent store: every hydrated chat threw on the next receipt or delete** 🩹💾 — hydration replaced the store's ordered-dictionary message bucket with a hand-rolled `{ array, get, upsert }`, but `makeInMemoryStore`'s handlers also call `updateAssign`, `filter` and `clear`. After a restart, the first delivery receipt, reaction or delete for a chat with persisted history threw a `TypeError` inside the event handler, and `writeToFile()` wrote a snapshot shape `readFromFile()` cannot read. Hydration now goes through the store's public `fromJSON()`. See BUGREPORT 2.68.
- **An ffmpeg path that exists but cannot be executed was accepted** 🩹🎬 — the resolver checked `existsSync` (and `setFfmpegPath()` checked nothing at all), so a file that lost its `+x` bit, a directory named `ffmpeg`, or a typo'd path was handed straight to `spawn()`: every ffmpeg consumer failed with a bare `EACCES`/`ENOENT` instead of the install guide, and a broken override silently masked a working `ffmpeg-static`/system binary. Candidates must now be an executable regular file; unusable ones are skipped (auto-detection continues) and the reason is reported. See BUGREPORT 2.67.
- **Only the first `groups.update` per group survived the event buffer** 🩹👥 — the consolidation branch read the buffered entry but wrote it back only when there wasn't one, so every later update for the same group was dropped without a log line. An offline sync carrying a subject change plus an admin-only toggle plus a new description delivered one of the three; a one-field notification arriving first discarded the full metadata refresh behind it. Updates now merge like every other bucket. See BUGREPORT 2.66.
- **Call audio was cut to its first 20 ms, then the uplink went dead** 🩹📞 — `AudioFeeder`'s metering loop was gated on the ffmpeg process still being alive, but ffmpeg decodes a short file in milliseconds and exits. The next tick returned early with up to 1024 chunks still queued, so a prerecorded greeting played for one 20 ms chunk and the uplink then stalled completely — not even the silence frames the module promises. The loop now follows the feeder's own lifetime (`stop()` ends it), draining the queue at real-time cadence and filling with silence afterwards. Affects `voip.call()`, `answerCall()`, `joinGroupCall()`, `startGroupCall()` and every `setAudioSource()` swap; `audioSource: 'silence'` was unaffected. See BUGREPORT 2.65.

### Fixed
- **`fancy-text` `script` style rendered 11 letters at the wrong weight — mixed bold and non-bold glyphs** 🩹🔤 — the `script` style uses the **bold**-script alphabet (base U+1D4D0), whose Unicode block is complete, but a leftover `SPECIALS.script` table injected the **non-bold** Letterlike glyphs (ℬ U+212C, ℰ U+2130, ℱ, ℋ, ℐ, ℒ, ℳ, ℛ, ℯ, ℊ, ℴ) for the letters B/E/F/H/I/L/M/R/e/g/o. Those 11 letters therefore rendered in a visibly lighter weight than the rest of the word (`styleText('ABE','script')` → a bold 𝓐 next to a light ℬ/ℰ). The specials belong only to styles whose block genuinely has holes (fraktur, double-struck), so the `script` entry was deleted outright — the offset formula already covers every bold-script letter contiguously. `fraktur` / `doubleStruck` / `circled` are unaffected. Covered by `tests/v246-fancytext-script.test.js`. See BUGREPORT §2.25.
- **`group-op-guard` under-reported `retryInMs` for multi-count operations** 🩹🚦 — `check(op, count)`'s "retry in N ms" hint was computed from the single oldest call (`list[0]`), so it only ever accounted for freeing **one** slot. When a request needed several slots to free up (`count > 1`, or a history over-filled via raw `record()`), the wait it reported was too short — a caller that slept exactly that long woke to find the op still rate-limited. In a repro (three adds under a max-3 window, then `check('add', 2)`) it reported `800ms` but was still blocked afterwards; the correct value is `900ms`. It now waits for the `needed = used + count - max`-th oldest call to expire; `count === 1` at the limit is unchanged. Covered by `tests/v246-groupopguard.test.js`. See BUGREPORT §2.24.
- **`attendance` consecutive-day streaks reset on every restart — the advertised streak feature was effectively non-functional** 🩹📋 — `createAttendance` tracks multi-day check-in streaks but, unlike every sibling manager (economy, level-system, tiers, reminders, …), shipped no `toJSON`/`load`, so the in-memory `streaks` map couldn't survive a process restart. Since these bots typically restart daily, each restart wiped the map and the next check-in recomputed the streak back to `1` — it could never grow. Added `toJSON()`/`load()` (plus `clear()`) that round-trip the streak state **and** any in-progress session (a restored session still rejects duplicate check-ins and keeps numbering); a >1-day gap after reload correctly restarts the streak at 1. Covered by `tests/v246-attendance-persistence.test.js`. See BUGREPORT §2.23.
- **`shop.load()` dropped `maxPerUser` + `category`, silently disabling the per-user purchase cap after a reload** 🩹🏪 — `createShop().load()` rebuilt catalog items by destructuring only some fields, so `maxPerUser` and `category` fell into the `...meta` bucket instead of the top level where `buy()` and `renderCatalog()` read them (`toJSON()` saved them fine — only reload lost them). Covered by `tests/v246-shop-persistence.test.js`. See BUGREPORT §2.22.
- **`invite-tracker` double-credited duplicate/replayed group-adds — inflated `active` counts and double invite rewards** 🩹📨 — `createInviteTracker` credited every `group-participants.update` `add` to its author unconditionally, but WhatsApp re-emits that event and history/app-state sync replays it, so one real membership often arrived several times. Each replay fired `onInvite` again (in the documented reward flow that's a **double payout** — the example grants 500 coins per invite) and pushed an inviter's `active` count past `1` for a single member, an impossible value that skewed the leaderboard. - **`anti-link` guard missed bare `www.` links glued to punctuation — a moderation bypass** 🩹🔗 — `extractLinks`/`createAntiLinkGuard`'s `URL_RE` matched bare-domain links only when the `www.` was preceded by whitespace or the start of the string (`(?:^|\s)www\.…`). - **`MessageScheduler` could send one scheduled message multiple times** 🩹⏰ — `processQueue()` is driven by `setInterval(checkInterval)`, which fires again **without awaiting** the previous run. - **AIRich card CTAs now normalize the action type to WhatsApp's canonical `OPEN_URL`** 🩹🔗 — `addCompact`/`addProfileCard` (`action_type`) and `addFooterAction` (`cta_type`) passed the caller's string straight to the wire, but WhatsApp's unified-response renderer matches the action **exactly** (`OPEN_URL`, not `open_url`/`openUrl`/`url`/`link`), so a lowercase or aliased value silently produced a dead tap target. No-op for already-correct input. Covered by `tests/v246-r32-webview-airich.test.js`. See BUGREPORT §2.17.
- **`level-system` XP cooldown now survives a save + reload** 🎚️ — `createLevelSystem` throttles XP to at most once per `cooldownMs` per user via a `lastXpAt` stamp, but `toJSON()` never serialized it and `load()` reset it to `0`, so a save + reload (a bot restart) wiped every user's cooldown and let them earn XP again on their very next message — the same persistence gap already fixed for the economy `lastWorkAt` and reputation `cooldowns` maps. `lastXpAt` is now persisted and restored; xp/messages/prestige round-trips are unchanged. Covered by `tests/v246-utils-upgrades.test.js`.
- **`compactNumber` no longer prints `1000K` / `1000M`** 🔢 — when rounding carried a scaled value up to the next unit's magnitude (`999_999 / 1e3 = 999.999` → `toFixed(1)` = `1000.0`), the abbreviation showed `1000K` / `1000M` instead of promoting to `1M` / `1B`. It now detects the carry and rolls into the larger unit. Every value that already formatted correctly is unchanged. Covered by `tests/v246-utils-upgrades.test.js`.
- **VoIP WASM bundle re-verified against live + a browser-free refresh path** 🧩 — the bundled VoIP WASM assets (`whatsapp.wasm`, `worker-modules.js`, `loader.js`) were re-verified **byte-for-byte** against WhatsApp Web's live CDN (all three sha256/size match the pins; `integrity.json` now records a `verifiedAgainstLiveAt` stamp). Separately, `scripts/fetch-wasm-resources.mjs` gained a **`pinned`** mode (`npm run voip:verify-wasm`) that re-downloads and re-verifies straight from the URLs already recorded in `integrity.json` — a robust, browser-free repair/verify path that doesn't depend on WhatsApp's occasionally-moving bootloader endpoint (now used as an automatic fallback before requiring a running Chrome). The pure verifier `verifyPinnedManifest(manifest, downloads)` is exported and covered by `tests/v246-wasm-integrity.test.js` (5 cases, incl. a real check of the bundled assets against the manifest + tamper/size/missing detection).
- **VoIP PCM helpers no longer crash on an odd-offset buffer (`RangeError: start offset of Int16Array should be a multiple of 2`)** 🎙️ — every `voip-tools` PCM helper viewed its input as 16-bit samples with a zero-copy `new Int16Array(buf.buffer, buf.byteOffset, …)`. `Int16Array` requires a **2-byte-aligned** `byteOffset`, but Node's pooled `Buffer`s and — far more commonly — `buf.subarray(oddIndex)` views (a call-audio frame sliced out of a larger buffer, or an RTP payload that lands on an odd byte offset) routinely start on an **odd** offset, which made the whole call throw before doing any work. In practice this meant `rmsLevel`/`peakLevelPcm`/`isSilentPcm`/`applyGainPcm`/`mixPcm`/`downmixStereoToMono` (the v2.4.5 audio-math batch) and `encodeMulaw`/`encodeAlaw`/`pcmToFloat32`/`concatPcm`/`slicePcmMs` (the v2.4.6 G.711/codec batch) crashed intermittently depending on how the caller obtained the buffer. Both internal coercers (`asInt16`, `toInt16Array`) now detect a misaligned `byteOffset` and copy the usable bytes into a fresh, aligned buffer first; the odd trailing byte is dropped as before. The already-aligned fast path is untouched and **byte-identical** — this only rescues inputs that previously threw, and an odd-offset frame now yields the exact same result as the aligned frame. Covered by `tests/v246-voip-pcm-alignment.test.js` (5 cases, incl. odd-offset↔aligned parity across every helper and an odd-offset+odd-length view). See BUGREPORT §2.12.
- **Interactive messages can now be sent without a media header or body text** 🔘 — buttons / list (`sections`) / `nativeFlow` / carousel messages that carry only buttons + a footer (no `text`, no `caption`, no media) used to throw `Invalid media type` from `prepareWAMessageMedia` before the interactive builder ever ran, so a body-less action-button message was impossible. The builder now detects an interactive message with no media and skips media prep, letting it build with an empty header; the legacy `buttons` path also tolerates the media-less case instead of crashing on `Object.keys(m)[0]`. Byte-identical for every message that already worked — this only rescues shapes that previously threw; a genuinely media-less *non-interactive* message still errors as before. Covered by `tests/v246-interactive-nobody.test.js` (4 cases).
- **Media-only nativeFlow interactive messages no longer crash** 🩹 — a `nativeFlow` interactive message with a media header but **no caption** (e.g. `{ nativeFlow, image }`) reached the builder's no-caption branch with the header still unbuilt and hit `Object.assign(undefined, m)`, throwing before the message could be sent. It now builds a proper media header instead. (The media-header-with-`text`-body combo is intercepted much earlier by the top-level `text` branch, which turns it into an extendedText body, so that path never reaches here.) Covered by `tests/v246-interactive-header.test.js` (3 cases).
- **Text-only / button-only carousel cards now work (+ a latent crash fixed)** 🎠 — building a carousel card without a resolvable media header threw `Invalid media type for carousel card`, so text-only cards — which WhatsApp renders fine — were impossible. Now a card that carries its own `text`/`caption` or `nativeFlow` buttons builds without a media header, while a card that *intended* media but failed to resolve still surfaces the original media error, and a truly empty card (no media, text, or buttons) is rejected with a clear message. Also fixed a latent `Object.assign(undefined, …)` crash that hit media-without-caption and button-only cards. Decision isolated in the pure helper `assessCarouselCard(card, isValidHeader)` (exported + typed). NOTE: we deliberately did **not** bump `messageVersion`/`flow_message_version`/`carouselCardType` magic numbers — those values are unverified against Meta and rot over time, so changing them is a rendering risk, not a correctness fix. Covered by `tests/v246-carousel-textonly.test.js` (7 cases) + updated `message-regression` carousel suite.
- **Group sender-key now rotates on membership change — fixes stuck "Waiting for this message" after a phone switch + a forward-secrecy gap** 🔐 — when a member left/was removed or switched phones, our fork never invalidated the stored group sender-key distribution memory (`sender-key-memory`), so the bot kept reusing the same sender key. Two consequences: a departed member could still decrypt every message the bot sent afterwards (forward-secrecy break), and a member who switched phones never received a fresh Sender Key Distribution Message, leaving their group messages stuck at "Waiting for this message" (WhiskeySockets/Baileys#2704 / #2730). Now `handleGroupNotification` invalidates `sender-key-memory[group]` on `remove`/`leave` (rotation for forward secrecy) and `modify`/number-change (re-distribution), so the next send generates a fresh sender key and distributes it to exactly the current devices — matching WhatsApp's lazy-rotation semantics. Decision extracted to the pure helper `resolveGroupSenderKeyReset(action)` (exported + typed). Covered by `tests/v246-group-senderkey-reset.test.js` (5 cases).
- **Persistent "Bad MAC" / undecryptable messages on LID↔PN session mismatch — now retried against the stanza's paired identity** 🚑 — `decryptMessageNode` picked a single identity form (LID or phone-number JID) per stanza and, on failure, gave up. When a device's Signal session was established under one form but a later stanza addressed it under the other (most reproducible on an account's own multi-device self-sync traffic), libsignal threw a **persistent `Bad MAC`** that a QR rescan or session reset never fixed. We already parsed the alternate form WhatsApp puts on the stanza itself (`sender_pn`/`sender_lid` for 1:1, `participant_pn`/`participant_lid` for groups) but never used it to recover. Now, on a `pkmsg`/`msg` decrypt failure, we retry **once** against that alternate identity (device-carried via `transferDevice`) before stubbing the message — and if the retry also fails we **preserve the original, more meaningful error** (not the alt-form's "no session"). Scoped to `pkmsg`/`msg` so unrelated failures (duplicate/old-counter, corrupt ciphertext) don't trigger a wasteful second attempt. New pure helper `getAlternateDecryptionJid(stanza, triedJid, author)` (exported + typed). Ported from WhiskeySockets/Baileys#2763 (with the reviewer's scoping/original-error improvements). Covered by `tests/v246-decrypt-altid-retry.test.js` (9 cases) and BUGREPORT §2.7.
- **AIRich tables now render natively — `__typename` was mis-spelled `GenATableUXPrimitive` (missing the `I`)** — the table primitive was emitted as `GenATableUXPrimitive` in both builders (`AIRich.addTable`, `rich-message-utils`) and matched under the same wrong name in the reader, so our own round-trip tests passed **but WhatsApp never rendered the table** — the real Meta primitive is `GenAITableUXPrimitive`, and every other primitive we emit already uses the `GenAI` prefix. All three sites now use `GenAITableUXPrimitive`; the reader also still accepts the legacy mis-spelling so any previously-stored payloads keep parsing. Independently corroborated by other Baileys forks documenting the identical fix. Covered by `tests/v246-airich-stacks.test.js` and BUGREPORT §2.6.
- **`LIDMappingStore` cache-TTL comment corrected (3 days, not 7)** — the LRU mapping cache is constructed with `ttl: 3 * 24 * 60 * 60 * 1000` but the inline comment read `// 7 days`, misdescribing the actual retention. The canonical LID-mapping store uses a 3-day TTL, so the comment (not the value) was wrong; it now reads `// 3 days`. Comment-only change — no behaviour change to cache eviction.
- **`encodeBinaryNode` no longer corrupts the wire on a non-string attribute** — the node's list-size header was computed from every non-null attribute, but the writer only emits string-valued ones (its `typeof === 'string'` guard). A stray number/boolean attribute therefore inflated the header by 2 while writing nothing, so the decoder read the following **content** bytes as the missing attribute pair and threw `invalid string with tag: …` — corrupting the whole node. The header now counts exactly the attributes written (string-valued), keeping header and body in lockstep; a non-string attr is cleanly dropped (the writer's long-standing intent) instead of desyncing the stream. Use `normalizeBinaryNodeAttrs`/`binaryNode` to stringify values you want preserved. Covered by `tests/v246-wabinary-codec.test.js` (incl. the exact repro). See BUGREPORT §2.5.
- **`kv-store` no longer leaks TTL shadow keys** — every key set with `{ ttlMs }` stores its expiry under a hidden `__ttl__:<key>` shadow key, but `delete(key)` removed only the value and `clear()` never matched shadow keys at all (they always contain `:` and never carry the namespace prefix, so both root and namespace `clear()` skipped them). Orphaned `__ttl__:` entries therefore accumulated unbounded in memory and on disk. `delete()` now also drops the shadow key, and `clear()` removes each matched key together with its shadow. TTL enforcement is unchanged. Covered by `tests/v246-kvstore-ttl-fix.test.js` (5 cases, incl. on-disk assertions).
- **`parseDuration` no longer accepts glued garbage** — the garbage-rejection guard was dead code: it tested `matchedLen === 0`, which is unreachable once a unit has matched, so inputs like `'x10m'` (glued prefix) and `'10m tomorrow'` (trailing word) were silently parsed as `10m` instead of rejected. It now requires the whole input (ignoring spaces/commas) to be duration tokens and returns `null` otherwise. All previously-valid forms (`'1h30m'`, `'2d 4h'`, `'0.5h'`, `'10ms'`→null) are preserved. Covered by `tests/v246-duration-parse.test.js`.
- **Custom pairing codes are no longer over-restricted to the Crockford alphabet** — an earlier build of this fork validated a *custom* pairing code against the Crockford base32 set and rejected `0`, `I`, `O`, `U`, so valid codes other WhatsApp clients accept (e.g. `OTHERCOD`, `SH1Z0D3V`) failed with a misleading error. WhatsApp does not restrict the custom-code alphabet — upstream WhiskeySockets/Baileys only length-checks it. `requestPairingCode` and `normalizePairingCode` now accept **any 8 alphanumeric characters (A-Z, 0-9)** (still stripping separators and upper-casing for the phone entry screen). The Crockford alphabet remains in use only for *auto-generated random* codes, where avoiding look-alike glyphs is desirable. Covered by the updated `tests/pairing-and-avatar.test.js`, `tests/pairing-and-community.test.js`, and `tests/v245-core-upgrades.test.js`.

## [2.1.0] - 2026-09-11

### Added
