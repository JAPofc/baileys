## [2.4.6] - 2026-09-30

> **Maintained by [JAP](https://whatsapp.com/channel/0029VbEVFrILtOjAOu4FXa3r).** A fork of [WhiskeySockets/Baileys](https://github.com/WhiskeySockets/Baileys) (upstream WhatsApp protocol) with a vendored QR generator by [Nayuki](https://github.com/nayuki/QR-Code-generator). This point release widens the AIRich builder (stack + raw/custom view_model primitives, `RichAI` brand alias), hardens the mini-app/webview flow (audience binding + one-time nonce anti-replay), adds a real native in-app WebView button (`open_webview`) to the `nativeFlow` shorthand + mini-app and fixes its pre-flight validation, normalizes AIRich card CTAs to WhatsApp's canonical `OPEN_URL`, makes `retryWithBackoff` cancelable via `AbortSignal`, gives `createWordFilter` and `createAntiLinkGuard` runtime allowlist/domain control plus an auto-delete toggle and match/detection counters, adds cross-chat `invite-tracker` aggregation (`getGlobalCount`/`getGlobalLeaderboard`), adds poll freezing + `selectableCount` enforcement + per-option voter lookup to `poll-manager`, adds shop `restock`/`getInventoryValue`/category-patchable `updateItem`, adds `attendance` persistence (`toJSON`/`load`) so consecutive-day streaks survive restarts, adds `group-op-guard` rate-limit persistence, adds a `fancy-text` `unstyleText` inverse (fancy Unicode → plain ASCII for search/moderation), fixes a `fancy-text` `script` style bug that rendered 11 letters at the wrong weight, fixes a `group-op-guard` bug that under-reported the retry delay for multi-count ops, fixes a `shop.load()` bug that dropped `maxPerUser`/`category` and disabled the per-user purchase cap after a reload, fixes an `anti-link` bypass where bare `www.` links glued to punctuation went undetected, fixes an `invite-tracker` bug that double-credited duplicate/replayed group-adds, fixes a `MessageScheduler` bug that could deliver one scheduled message multiple times, extends the VoIP and bot-framework toolkits (throttled broadcaster + timed scheduler), fixes native table rendering, recovers from persistent LID↔PN "Bad MAC" decrypt failures (upstream #2763), rotates the group sender-key on membership change (fixes stuck "Waiting for this message" + a forward-secrecy gap, #2704/#2730), adds decrypt-failure observability + on-by-default log-flood protection (`messages.decrypt-failed` event and the `decryptFailureLog` option / `createDecryptFailureTracker`, #2234), locks in memory-safety regressions for the mutex/event-buffer, enables text-only carousel cards, hardens the interactive-message builder (media-only crash fixed; body-less buttons/list/nativeFlow/carousel now sendable), fixes an odd-byte-offset crash in the VoIP PCM helpers, restores the level-system XP cooldown across reloads and the `compactNumber` unit-carry, re-verifies the VoIP WASM bundle against live (with a browser-free refresh path), adds Signal LID↔PN mapping-store coverage, and upgrades the permanent startup banner to v5 (automatic per-run colour/theme, true-color gradients with 256-color fallback, `FORCE_COLOR`/`NO_COLOR` support read at call time, a clickable OSC-8 repo link, a live release-stats line, and a pure `renderBanner()`). Includes a supply-chain safety audit against the documented malicious-fork campaign (BUGREPORT §2.11). **1237 tests green, `tsc` clean.**

### Added
- **Startup banner v4/v5 — automatic per-run colour, true-color gradients, `FORCE_COLOR` support, a clickable repo link, a live "what's new" line, and a pure `renderBanner()`** 🆕🍃 — the permanent startup banner got a big quality pass. **Colour is now automatic every run**: the banner picks a **fresh random theme + tagline on each process start** (override with `JAP_BANNER_THEME=leaf|ocean|sunset|violet|aurora|ember` to pin one, or `=daily` for the old once-a-day rotation, or `=random` to be explicit). Gradients render in **24-bit true-color** when the terminal advertises it (`COLORTERM=truecolor|24bit`), gracefully falling back to the 256-color palette otherwise. Colour opt-out/opt-in follows the ecosystem conventions **read at call time**: `NO_COLOR` (or `FORCE_COLOR=0`) turns colour off (the banner still prints), and **`FORCE_COLOR=1|2|3` forces the full colour banner even off a TTY** (CI/pm2 dashboards; `=3` forces true-color). The GitHub link is a real **OSC-8 hyperlink** (clickable in modern terminals, plain text in older ones); a new line reads the **latest CHANGELOG section live** and shows the release date plus this release's added/fixed counts (so it stays correct every release with no edits here); two more pinnable themes were added (`aurora`, `ember`); and rendering is decoupled from output via a pure **`renderBanner(opts?)`** that returns the lines (testable/embeddable) — `printBanner()` just writes them. `NO_COLOR` keeps the nicer boxed layout, just uncolored. The banner remains a permanent, non-disableable part of the package. Typed in `banner.d.ts` (new `renderBanner` + `BANNER_THEMES` exports), covered by `tests/v246-banner-v4.test.js` (8 cases).
- **`fancy-text` gains `unstyleText` — turn fancy Unicode text back into plain ASCII** 🆕🔤 — the module could style text into a dozen Unicode variants but had no way back, so bots couldn't search, moderate, or normalize fancy display names / captions (a scammer's `𝓙𝓸𝓱𝓷` sailed past a plain-text word filter). `unstyleText(text)` maps every styled letter/digit — all offset styles plus small-caps and the fraktur / double-struck / circled "holes" — back to ASCII; unknown characters (emoji, punctuation) pass through unchanged. Small-caps normalizes to lowercase (the alphabet has no case) and order-reversed `upsideDown` is intentionally left alone (lossy). Built from the same tables `styleText` uses, so the two stay in sync automatically. Typed in `fancy-text.d.ts`, covered by `tests/v246-fancytext-script.test.js`.
- **`createGroupOpGuard` gains rate-limit persistence — `toJSON()` / `load()`** 🆕🚦 — the guard's recent-operations history can now be saved and restored, so a bot that restarts (or crash-loops) doesn't forget the group ops it just did and immediately blast past WhatsApp's ceilings again. Serializes the pruned per-op timestamps; restored entries still age out normally. Typed in `group-op-guard.d.ts`, covered by `tests/v246-groupopguard.test.js`.
- **`createAttendance` gains persistence — `toJSON()` / `load()` / `clear()`** 🆕📋 — attendance can now save and restore its full state, so consecutive-day streaks (and an in-progress roll-call session) survive a restart instead of resetting. Typed in `attendance.d.ts`, covered by `tests/v246-attendance-persistence.test.js`.
- **`createShop` gains `restock`, `getInventoryValue`, and category-patchable `updateItem`** 🆕🏪 — `restock(id, qty)` bumps an item's stock relatively (vs. `updateItem`'s absolute set; `Infinity` stock is left untouched), `getInventoryValue(user)` totals a user's inventory at sell-back value (`floor(price*sellRate)*qty`, items no longer in the catalog count as 0) for net-worth/rich-list math, and `updateItem` can now patch `category` (previously only settable at `addItem`). Additive — existing shop behaviour unchanged. Typed in `shop.d.ts`, covered by `tests/v246-shop-persistence.test.js`.
- **`createPollManager` gains poll freezing, `selectableCount` enforcement, and per-option voter lookup** 🆕🗳️ — the stateful poll manager accepted votes forever and never enforced a poll's select limit. Now **`close(idOrMsg)` / `reopen(idOrMsg)` / `isOpen(idOrMsg)`** freeze and resume a poll (once closed, `applyVote`/`applyUpdate` stop recording and just return the frozen tally — e.g. at a deadline), `applyVote` **honours `selectableCount`** so a malformed/over-selection can never record more picks than the poll allows (a no-op for well-behaved clients; keeps option order), and **`getVotersFor(idOrMsg, nameOrIndex)`** lists the voters currently on a given option. Additive — tallying and the existing API are unchanged. Typed in `poll-manager.d.ts`, covered by `tests/v246-pollmanager-upgrade.test.js`.
- **`createInviteTracker` gains cross-chat aggregation — `getGlobalCount` / `getGlobalLeaderboard`** 🆕📨 — the tracker only answered per-chat questions, but bots that reward inviting anywhere need totals across every group. `getGlobalCount(inviter)` returns an inviter's combined `{ total, active }` across all tracked chats, and `getGlobalLeaderboard(limit?)` ranks inviters globally (by active, then total). Additive — per-chat methods unchanged. Typed in `invite-tracker.d.ts`, covered by `tests/v246-invite-tracker.test.js`.
- **`createAntiLinkGuard` gains runtime allowlist + allowed-domain control, an auto-delete toggle, and detection counters** 🆕🔗 — like the word filter, the anti-link guard froze its `allowlist` and `allowedDomains` at creation. Now **`allow(...chats)` / `unallow(...chats)` / `isAllowed(chat)` / `getAllowlist()`** manage exempt chats live, **`allowDomain(...domains)` / `disallowDomain(...domains)` / `getAllowedDomains()`** manage whitelisted link domains (non-invite mode), **`setAutoDelete(on)`** toggles delete-for-everyone (with an `autoDelete` getter), and **`stats`** exposes `{ detected, deleted }`. All additive — detection/invite paths unchanged. Typed in `anti-link.d.ts`, covered by `tests/v246-antilink-runtime.test.js`.
- **`createWordFilter` gains runtime allowlist control, an auto-delete toggle, and match counters** 🆕🛡️ — the word filter already let you add/remove banned words at runtime, but its allowlist (chats exempt from filtering) and `autoDelete` were frozen at creation, and there was no way to see how much it had caught. Now: **`allow(...chats)` / `unallow(...chats)` / `isAllowed(chat)` / `getAllowlist()`** manage exempt chats live (each accepts one jid or several/arrays); **`setAutoDelete(on)`** flips delete-for-everyone on matches after creation (with an `autoDelete` getter); and **`stats`** exposes running `{ matches, deleted }` counters. Purely additive — existing behaviour and the match/censor paths are unchanged. Typed in `word-filter.d.ts` and covered by `tests/v246-wordfilter-runtime.test.js` (3 cases).
- **`retryWithBackoff` now supports an `AbortSignal` — cancel a retry loop cleanly** 🆕🛑 — long backoff waits (media upload / mex retries can climb to 30 s) used to be uninterruptible: once `retryWithBackoff` was sleeping between attempts, nothing could stop it short of letting it run out. It now accepts a `signal` option — an already-aborted signal rejects **before** the first attempt (so `fn` never runs), and an abort that lands **during** a backoff wait rejects immediately instead of waiting the delay out. The rejection is the signal's `reason` when set, otherwise an `Error` with `name: 'AbortError'` (matching the DOM/undici convention), so callers can `catch`-and-ignore cancellations the usual way. Pair it with `AbortSignal.timeout(ms)` for a hard ceiling on the whole retry loop. Fully backward compatible — omitting `signal` behaves exactly as before. New helper `createAbortError(reason?)` is exported + typed. Covered by `tests/v246-retry.test.js` (4 new cases).
- **Real native in-app WebView button (`open_webview`) is now reachable from the `nativeFlow` shorthand + mini-app** 🆕🪟 — `open_webview` (a true titled in-app web view) already existed in the `Button` builder and the `button-sender` validator, but the terse `nativeFlow` shorthand converter (`prepareNativeFlowButtons`) had **no branch for it**, so the only way to fake an in-app view was `cta_url`'s `webview_interaction` flag — which modern WhatsApp clients simply **ignore** (verified against the official `cta_url` params `{display_text, url, merchant_url}`). You can now pass `{ webview: 'https://…' }` or `{ webview: { url, title?, inAppWebview? } }` (alias key `openWebview`) in a `nativeFlow` array and it emits the correct wire shape `{ name:'open_webview', buttonParamsJson:{ title, link:{ url, in_app_webview } } }`, matching the shipped `Button.addOpenWebview` primitive. `buildMiniAppContent` gains an **opt-in `openWebview: true`** that routes the app link through this real webview button; the default stays `cta_url` (which renders on regular, non-Business accounts, whereas `open_webview` needs the in-app-webview capability) so no existing caller regresses. Plain `url` buttons are byte-identical to before. Covered by `tests/v246-r32-webview-airich.test.js`.
- **`messages.decrypt-failed` event — observe decryption failures instead of scraping logs** 🆕📡 — a new socket event fired alongside the `CIPHERTEXT` stub whenever an inbound message fails to decrypt, carrying `{ key, error, willRetry }`. Apps can now drive metrics/alerting or proactively reset a dead session without parsing log lines — the observability hook requested in WhiskeySockets/Baileys#2234. `willRetry` reflects whether Baileys will send a retry receipt (false for missing-keys and plaintext/CTWA "message absent" cases). Backed by the pure builder `buildDecryptFailureEvent(msg)` (returns `undefined` for non-failures and `peer`-category sync messages), wired as a one-line emit in `messages-recv`. Exported + typed, covered by `tests/v246-decrypt-failed-event.test.js` (6 cases).
- **`decryptFailureLog` socket option — decrypt-failure log-flood protection is now ON by default** 🆕🛡️ — the new `createDecryptFailureTracker` is auto-wired into every socket via a `decryptFailureLog` config option (default `{ windowMs: 60000, maxPerWindow: 5 }`), so a dead session can no longer flood logs / exhaust the heap out of the box (WhiskeySockets/Baileys#2234). Pass an options object to tune the window/budget, or `decryptFailureLog: false` to restore the old unlimited per-failure logging. Resolution is handled by the pure helper `resolveDecryptFailureTracker(config)` (exported + typed). Covered by the tests below (default-on, `false`-disables, options-forwarded).
- **`createDecryptFailureTracker` — rate-limited/de-duplicated decrypt-failure logging** 🆕🚀 — a dead Signal session (Bad MAC / no-session) can fail on every inbound stanza, and each failure builds a full `Error`+stack and a heavy log line — in the field this floods logs and exhausts the heap (WhiskeySockets/Baileys#2234). This pure, clock-injectable tracker collapses repeated failures **per session key** into at most `maxPerWindow` log lines per `windowMs`, counting how many were suppressed so the caller can summarize the backlog (`hit(key) → { log, occurrences, suppressedSincePrevWindow }`, plus `suppressedFor`/`size`/`clear`). It's wired into `decryptMessageNode` as an **opt-in** 6th arg (`{ failureTracker }`) — when passed, only the error *log* is rate-limited; the `CIPHERTEXT` message stub is **always** set (message correctness is never suppressed), and default behaviour without a tracker is unchanged. Exported + typed (`DecryptFailureTracker`), covered by `tests/v246-decrypt-failure-tracker.test.js` (11 cases).
- **`RichAI` brand alias + `META_RICH_PREFIX` protocol constant — clarified GenAI naming** 🆕 — the rich-message builder is now also exported as **`RichAI`** (the JAPofc brand name; `RichAI === AIRich`) alongside the existing `AIJap`/`JapAI`/`JapRich` aliases. To make the `GenAI…` naming unambiguous: those `__typename` strings are **Meta/WhatsApp's own wire-protocol vocabulary** for the unified-response format — not our branding and not a third-party credit — and the recipient's WhatsApp client matches on them byte-for-byte to render each card natively, so they are protocol-fixed. The prefix is now pinned in one exported constant `META_RICH_PREFIX` (with a prominent NAMING NOTE in `AIRich.js`) and consumed by the layout builders, so our source carries no bare "GenAI" branding while the wire stays correct. No behaviour change.
- **AIRich `addViewModel` / `addRawPrimitive` — raw custom view_model escape hatches** 🆕🚀 — Meta ships new unified-response primitives constantly, so rather than waiting for a dedicated `add*()` helper you can now emit **any** view_model or primitive by name. `addViewModel(typename, primitives, { extra, viewModel, fallback })` pushes a custom section — `typename` may be bare (`'HStackLayoutViewModel'`) or fully-qualified (`'GenAIHStackLayoutViewModel'`; Meta's prefix is added if missing), `primitives` is one spec or an array (each run through the new `AIRich.primitive(spec)` normalizer — a string becomes markdown text, `{ typename, ...props }` becomes that primitive), `extra`/`viewModel` merge custom fields onto the wrapper/view_model, and `fallback` pushes a plain-text submessage. `addRawPrimitive(typename, props, opts)` is the one-liner for dropping a single un-covered primitive (wrapped in a `SingleLayoutViewModel`). Registered as `EXPERIMENTAL_METHODS`, typed (`AIRichPrimitiveSpec`, `AIRichViewModelOptions`), and covered by `tests/v246-airich-raw-viewmodel.test.js` (11 cases, incl. a readback of a totally-unknown primitive).
- **Mini-app / webview security upgrade — audience binding + single-use nonce anti-replay** 🆕🚀 — a signed opener link (`createMiniAppLink`) used to be replayable by anyone until it expired. Two new signed claims close that: `audience` binds a link to a single opener (e.g. the recipient JID) — `parseMiniAppParams`/`verifyMiniAppRequest` throw `Boom(403)` "audience mismatch" for anyone else — and `nonce` pairs with the new **`createNonceStore({ ttlMs, max, now })`** (a single-use token store: `issue()` mints a nonce, `consume()` returns `true` exactly once and `false` for unknown/used/expired) so a captured link works **once** and every replay is `403`. Both claims are covered by the HMAC signature (tampering fails on the signature first), and the store takes an injectable clock. Typed (`NonceStore`, `MiniAppLinkOptions`, `MiniAppVerifyOptions`) and covered by `tests/v246-miniapp-webview.test.js` (8 cases).
- **AIRich `addHStack` / `addVStack` — SwiftUI-style stack layout primitives** 🆕🚀 — the unified-response layer already used `GenAISingleLayoutViewModel` and `GenAIActionRowLayoutViewModel`, but there was no way to lay child primitives out as an explicit horizontal or vertical stack. `addHStack(items)` emits **`GenAIHStackLayoutViewModel`** and `addVStack(items)` emits **`GenAIVStackLayoutViewModel`**, each with a `primitives` array. Items are terse specs coerced to the right primitive: a bare string or `{ text, heading }` → `GenAIMarkdownTextUXPrimitive`, `{ image, tapLinkUrl, alignment }` → `GenAIInlineImageUXPrimitive`, `{ spacer:true }` / `{ divider:true }` → the spacer/divider primitives, and `{ primitive }` passes a raw primitive through. Invalid items are dropped (empty stack throws), and a concatenated plain-text submessage is pushed so the bubble is never empty. Because `readRichMessage` already walks `view_model.primitives`, the stacked children read straight back with no reader changes. Registered as `EXPERIMENTAL_METHODS`, typed in `AIRich.d.ts` (new `AIRichStackItem`), and covered by `tests/v246-airich-stacks.test.js` (8 cases).
- **Framework `createBroadcaster` + `createScheduler` — throttled fan-out sending and timed job dispatch** 🆕🚀 — the framework could route inbound commands but had no first-class way to *push* a message to many chats safely, or to fire one later. `createBroadcaster({ send, throttleMs, maxRetries, retryDelayMs, onProgress, sleep })` fans a message out to a deduped recipient list at a rate-limited pace: it retries a failing send up to `maxRetries` (with a delay), reports per-recipient `onProgress`, and returns a handle — `{ cancel(), cancelled, done }` — whose `done` resolves to `{ total, sent, failed, cancelled, skipped, results }`. `broadcast(recipients, msg)` takes either a fixed message or a `(jid, index) => message` factory (for per-recipient personalization), throttles *between* recipients (never after the last, never once cancelled), and abandons in-flight recipients cleanly on `cancel()`. `createScheduler({ now, setTimer, clearTimer, onError })` is the timing half: `scheduleAt(date|ts, task)` / `scheduleAfter(ms, task)` register one-shot jobs, `cancel(id)` / `cancelAll()` drop them, and `list()` / `size` introspect the queue — and long delays are **re-armed in chunks** so a job scheduled beyond the signed-32-bit `setTimeout` ceiling (~24.8 days) fires at the right wall-clock moment instead of overflowing to almost-immediately. Both are transport-agnostic and take an injectable clock/timer/sleep, so they unit-test with zero sockets and zero real waiting. Compose them for the classic "scheduled broadcast". Exported from the Framework and top-level barrels, fully typed, and covered by `tests/v246-broadcaster.test.js` (15 cases).
- **`lib/Signal` LID↔PN mapping-store test coverage** 🆕 — a behaviour suite for `LIDMappingStore` (the store that keeps the fork's LID-addressed messages decryptable), driven by an in-memory `keys` mock so it needs no socket or DB: forward `getLIDForPN` (device-0 and device-separated `pn:3 → lid:3`), reverse `getPNForLID` **including the hosted companion (`@hosted.lid`) reverse path** (regression lock on the JAP@Fix that stopped hosted devices being silently skipped), idempotent `storeLIDPNMappings` (no duplicate write for an existing pair), cold-cache DB fallback, USync fill-in via `pnToLIDFunc`, and in-flight request coalescing (concurrent identical lookups share one fetch). No behaviour change; +13 tests locking in the current contracts (`tests/v246-lid-mapping.test.js`).
- **VoIP `createCallBridge` — end-to-end WhatsApp ⇆ RTP/SIP audio bridge** 🆕🚀 — the VoIP toolkit had all the pieces (G.711 transcode, RTP packetize/parse, jitter buffer) but nothing wiring them into a working call bridge. `createCallBridge({ codec, ssrc, samplesPerFrame, jitterCapacity, onRtp, onPcm })` is that glue, and it owns NO sockets — you feed it audio and RTP, it hands you RTP and audio through callbacks, so it runs (and unit-tests) with no network or WASM. `sendAudio(pcm, { marker })` is the WA→SIP path: it transcodes linear 16-bit PCM to G.711 (μ-law/A-law) and emits one RTP packet per `samplesPerFrame` frame (short trailing frame handled, marker bit on talkspurt start, sequence/timestamp advanced correctly). `receiveRtp(rtp)` is the SIP→WA path: it parses and jitter-buffers inbound packets (drops dups/late), and `drainAudio({ force })` pops them in order, decodes to PCM, and emits each frame via `onPcm` (returns `{ frames, pcm }`). Plus `stats()` (frames sent/delivered + packetizer + jitter counters) and `close()`. A full loopback (bridge A → RTP → bridge B) reconstructs the sample count and waveform. Pure, typed, exported from the Utils barrel, covered by `tests/v246-call-bridge.test.js` (11 cases).
- **Interactive `Button` builder — pre-flight `validate()` / `assertValid()` + introspection** 🆕🚀 — the native-flow `Button` builder had no way to catch mistakes before WhatsApp silently rejected or mis-rendered a card. `validate()` returns `{ ok, errors, warnings }` after a socket-free inspection of the accumulated buttons: it flags an empty card, malformed `buttonParamsJson`, missing `display_text`/`id`/`url`/`phone_number`/`copy_code`, invalid CTA URLs, duplicate `quick_reply` ids, single_select rows with no id, and more than one single_select — and warns about >10 buttons or a single_select mixed with other buttons. `assertValid()` throws on any error (chainable), and `send(jid, { validate: true })` opts a card into that guard before relaying. Plus `getButtonNames()` / `countButtons()` for introspection. Typed and covered by `tests/v246-button-validate.test.js` (10 cases).
- **Deep `lib/WABinary` encode/decode round-trip coverage** 🆕 — a dedicated codec suite locking in the wire format across JID kinds (pair/AD-device/lid), packed strings (nibble/hex, odd length), dictionary tokens, buffers spanning the BINARY_8/BINARY_20 boundary, dropped null attributes, deeply nested lists, and the `decodeBinaryNode` 0x00-prefix path — plus a regression lock on the fix below. `tests/v246-wabinary-codec.test.js` (12 cases).
- **Mini App toolkit upgrade — signed + expiring deep links, request verification, and in-chat submission reading** 🆕🚀 — the Mini App sender could build a signed deep link, but a signature with no expiry can be replayed forever, there was no server-side verify helper, and nothing read a Flow submission coming back. This closes the whole loop. `createMiniAppLink(url, params, { secret, expiresIn, now })` now signs an **`exp`** into the payload (lifetime in seconds; the signature covers it, so expiry is tamper-proof), and `parseMiniAppParams(link, { secret, now })` **enforces** it (`Boom(403)` on an expired or forged link) — both take an injectable clock. New `verifyMiniAppRequest(input, { secret })` is the web-app-side counterpart: it accepts a full URL, a raw query string, or a params object (e.g. Express `req.query`) and returns the clean, verified params. `buildMiniAppContent` gained `secret`/`expiresIn` so the **CTA URL it emits is signed/expiring** (unsigned and byte-for-byte backward-compatible when neither is given). New `parseMiniAppResponse(msg)` reads an in-chat Flow/mini-app submission (`interactiveResponseMessage.nativeFlowResponseMessage`, unwrapping viewOnce/ephemeral) into `{ name, version, params, flowToken, body }` (invalid JSON degrades to `{}`, non-responses → `null`). Plus `buildFlowNavigate(screen, data, opts)` to pair with `buildFlowDataExchange` — the correct `{ action:'navigate', data:{ screen, … } }` shape for `flow.actionPayload`. All pure/typed, exported from the Utils barrel, and covered by `tests/v246-mini-app-upgrade.test.js` (16 cases; existing `tests/mini-app.test.js` still green).
- **`CommandRouter` — a batteries-included command dispatcher for the Bot framework** 🆕🚀 — the framework only shipped `Bot.command()`, which does bare word-boundary prefix matching; every real bot then re-implements the same plumbing by hand. `CommandRouter` provides all of it as ONE middleware you drop into the existing `use()` chain: **multiple prefixes** (`['!','/','.']`), **aliases**, **quote-aware argument + `--flag` parsing** (reusing the vendored `args-parser`, exposed on the handler ctx as `ctx.args`/`ctx.flags`/`ctx.command`/`ctx.argString`), **per-user cooldowns** (owner-exempt, reports `remainingMs`, auto-released if the handler throws), **permission gates** (`ownerOnly` — device-agnostic owner match, `groupOnly`, `privateOnly`, `adminOnly` via an injectable/socket-backed resolver, `botAdmin`, and arbitrary `permission(ctx)`), a **help screen** that stays in sync with the registry (`help()` grouped by category + `describe(name)` for one command), and lifecycle hooks (`onUnknown`/`onPermissionDenied`/`onCooldown`/`onError`). The dispatch core is clock-injectable and socket-free, so it unit-tests against a plain mock ctx. Wired into `Bot` via `bot.createRouter(opts)` (auto-backs the group-admin gate with the live socket) and `bot.useRouter(router)`; `Context` gains the getters the router keys off — `isGroup`, `sender` (group participant, else chat JID), `isFromMe`, `pushName`, `mentionedJids`. Plus `createGroupAdminResolver(sock, { cacheMs })` (TTL-cached group-admin lookup). Exported from the Framework and top-level barrels, fully typed, and covered by `tests/v246-command-router.test.js` (19 cases).
- **`retry` — async retry with exponential backoff** 🆕 — WhatsApp network calls (media upload, mex queries, profile fetches) fail transiently; `retryWithBackoff(fn, opts)` wraps one in a bounded retry loop with exponential backoff + optional full jitter, `shouldRetry`/`onRetry` hooks, and an injectable `sleep` (testable without real timers). The builder now detects an interactive message with no media and skips media prep, letting it build with an empty header; the legacy `buttons` path also tolerates the media-less case instead of crashing on `Object.keys(m)[0]`. Byte-identical for every message that already worked — this only rescues shapes that previously threw; a genuinely media-less *non-interactive* message still errors as before. Covered by `tests/v246-interactive-nobody.test.js` (4 cases).
- **Media-only nativeFlow interactive messages no longer crash** 🩹 — a `nativeFlow` interactive message with a media header but **no caption** (e.g. `{ nativeFlow, image }`) reached the builder's no-caption branch with the header still unbuilt and hit `Object.assign(undefined, m)`, throwing before the message could be sent. It now builds a proper media header instead. (The media-header-with-`text`-body combo is intercepted much earlier by the top-level `text` branch, which turns it into an extendedText body, so that path never reaches here.) Covered by `tests/v246-interactive-header.test.js` (3 cases).
- **Text-only / button-only carousel cards now work (+ a latent crash fixed)** 🎠 — building a carousel card without a resolvable media header threw `Invalid media type for carousel card`, so text-only cards — which WhatsApp renders fine — were impossible. Now a card that carries its own `text`/`caption` or `nativeFlow` buttons builds without a media header, while a card that *intended* media but failed to resolve still surfaces the original media error, and a truly empty card (no media, text, or buttons) is rejected with a clear message. Also fixed a latent `Object.assign(undefined, …)` crash that hit media-without-caption and button-only cards. Decision isolated in the pure helper `assessCarouselCard(card, isValidHeader)` (exported + typed). NOTE: we deliberately did **not** bump `messageVersion`/`flow_message_version`/`carouselCardType` magic numbers — those values are unverified against Meta and rot over time, so changing them is a rendering risk, not a correctness fix. Covered by `tests/v246-carousel-textonly.test.js` (7 cases) + updated `message-regression` carousel suite.
- **Group sender-key now rotates on membership change — fixes stuck "Waiting for this message" after a phone switch + a forward-secrecy gap** 🔐 — when a member left/was removed or switched phones, our fork never invalidated the stored group sender-key distribution memory (`sender-key-memory`), so the bot kept reusing the same sender key. Two consequences: a departed member could still decrypt every message the bot sent afterwards (forward-secrecy break), and a member who switched phones never received a fresh Sender Key Distribution Message, leaving their group messages stuck at "Waiting for this message" (WhiskeySockets/Baileys#2704 / #2730). Now `handleGroupNotification` invalidates `sender-key-memory[group]` on `remove`/`leave` (rotation for forward secrecy) and `modify`/number-change (re-distribution), so the next send generates a fresh sender key and distributes it to exactly the current devices — matching WhatsApp's lazy-rotation semantics. Decision extracted to the pure helper `resolveGroupSenderKeyReset(action)` (exported + typed). Covered by `tests/v246-group-senderkey-reset.test.js` (5 cases).
- **Persistent "Bad MAC" / undecryptable messages on LID↔PN session mismatch — now retried against the stanza's paired identity** 🚑 — `decryptMessageNode` picked a single identity form (LID or phone-number JID) per stanza and, on failure, gave up. When a device's Signal session was established under one form but a later stanza addressed it under the other (most reproducible on an account's own multi-device self-sync traffic), libsignal threw a **persistent `Bad MAC`** that a QR rescan or session reset never fixed. We already parsed the alternate form WhatsApp puts on the stanza itself (`sender_pn`/`sender_lid` for 1:1, `participant_pn`/`participant_lid` for groups) but never used it to recover. Now, on a `pkmsg`/`msg` decrypt failure, we retry **once** against that alternate identity (device-carried via `transferDevice`) before stubbing the message — and if the retry also fails we **preserve the original, more meaningful error** (not the alt-form's "no session"). Scoped to `pkmsg`/`msg` so unrelated failures (duplicate/old-counter, corrupt ciphertext) don't trigger a wasteful second attempt. New pure helper `getAlternateDecryptionJid(stanza, triedJid, author)` (exported + typed). Ported from WhiskeySockets/Baileys#2763 (with the reviewer's scoping/original-error improvements). Covered by `tests/v246-decrypt-altid-retry.test.js` (9 cases) and BUGREPORT §2.7.
- **AIRich tables now render natively — `__typename` was mis-spelled `GenATableUXPrimitive` (missing the `I`)** — the table primitive was emitted as `GenATableUXPrimitive` in both builders (`AIRich.addTable`, `rich-message-utils`) and matched under the same wrong name in the reader, so our own round-trip tests passed **but WhatsApp never rendered the table** — the real Meta primitive is `GenAITableUXPrimitive`, and every other primitive we emit already uses the `GenAI` prefix. All three sites now use `GenAITableUXPrimitive`; the reader also still accepts the legacy mis-spelling so any previously-stored payloads keep parsing. Independently corroborated by other Baileys forks documenting the identical fix. Covered by `tests/v246-airich-stacks.test.js` and BUGREPORT §2.6.
- **`LIDMappingStore` cache-TTL comment corrected (3 days, not 7)** — the LRU mapping cache is constructed with `ttl: 3 * 24 * 60 * 60 * 1000` but the inline comment read `// 7 days`, misdescribing the actual retention. The canonical LID-mapping store uses a 3-day TTL, so the comment (not the value) was wrong; it now reads `// 3 days`. Comment-only change — no behaviour change to cache eviction.
- **`encodeBinaryNode` no longer corrupts the wire on a non-string attribute** — the node's list-size header was computed from every non-null attribute, but the writer only emits string-valued ones (its `typeof === 'string'` guard). A stray number/boolean attribute therefore inflated the header by 2 while writing nothing, so the decoder read the following **content** bytes as the missing attribute pair and threw `invalid string with tag: …` — corrupting the whole node. The header now counts exactly the attributes written (string-valued), keeping header and body in lockstep; a non-string attr is cleanly dropped (the writer's long-standing intent) instead of desyncing the stream. Use `normalizeBinaryNodeAttrs`/`binaryNode` to stringify values you want preserved. Covered by `tests/v246-wabinary-codec.test.js` (incl. the exact repro). See BUGREPORT §2.5.
- **`kv-store` no longer leaks TTL shadow keys** — every key set with `{ ttlMs }` stores its expiry under a hidden `__ttl__:<key>` shadow key, but `delete(key)` removed only the value and `clear()` never matched shadow keys at all (they always contain `:` and never carry the namespace prefix, so both root and namespace `clear()` skipped them). Orphaned `__ttl__:` entries therefore accumulated unbounded in memory and on disk. `delete()` now also drops the shadow key, and `clear()` removes each matched key together with its shadow. TTL enforcement is unchanged. Covered by `tests/v246-kvstore-ttl-fix.test.js` (5 cases, incl. on-disk assertions).
- **`parseDuration` no longer accepts glued garbage** — the garbage-rejection guard was dead code: it tested `matchedLen === 0`, which is unreachable once a unit has matched, so inputs like `'x10m'` (glued prefix) and `'10m tomorrow'` (trailing word) were silently parsed as `10m` instead of rejected. It now requires the whole input (ignoring spaces/commas) to be duration tokens and returns `null` otherwise. All previously-valid forms (`'1h30m'`, `'2d 4h'`, `'0.5h'`, `'10ms'`→null) are preserved. Covered by `tests/v246-duration-parse.test.js`.
- **Custom pairing codes are no longer over-restricted to the Crockford alphabet** — an earlier build of this fork validated a *custom* pairing code against the Crockford base32 set and rejected `0`, `I`, `O`, `U`, so valid codes other WhatsApp clients accept (e.g. `OTHERCOD`, `SH1Z0D3V`) failed with a misleading error. WhatsApp does not restrict the custom-code alphabet — upstream WhiskeySockets/Baileys only length-checks it. `requestPairingCode` and `normalizePairingCode` now accept **any 8 alphanumeric characters (A-Z, 0-9)** (still stripping separators and upper-casing for the phone entry screen). The Crockford alphabet remains in use only for *auto-generated random* codes, where avoiding look-alike glyphs is desirable. Covered by the updated `tests/pairing-and-avatar.test.js`, `tests/pairing-and-community.test.js`, and `tests/v245-core-upgrades.test.js`.

### Fixed
- **In-memory store consistency** — every event handler resolved the message bucket with a different jid (raw vs `remoteJidAlt` vs normalized), so receipts, reactions, deletes and status updates could silently miss messages stored under device-suffixed or LID-alt keys (all reproduced).
